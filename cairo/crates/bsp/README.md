# bsp

**Does**: two operations on a binary space partition, over data it does not
own. `point_in_subsector` descends to the leaf containing a point
(`R_PointInSubsector`); `cross_bsp` walks every subsector a segment crosses,
nearest first, calling a caller-supplied `SubsectorVisitor` and stopping as
soon as one returns `false` (`P_CrossBSPNode`, the traversal `P_CheckSight`
and `P_PathTraverse` are built on). `Nodes` is a bundle of spans over the
planar arrays the WAD tool generates — three biased half-plane coefficient
arrays, two child arrays, eight bbox felts per node — with `is_subsector`,
`subsector_of`, `child_box` and `trace` (which hoists both endpoints once).

**Does not**: build a tree (that is offline, in `tools/wad`), own level
data, map a subsector to its sector (`doom_map` generates `SS_SECTOR`; S1 §7:
never walk SEGS → LINEDEF → SIDEDEF → SECTOR at run time), or know what a
sight line is blocked *by* — the visitor decides that.

**Invariants**:

* a child id is a node index below `SUBSECTOR_FLAG` (`0x80000000`) and a
  subsector above it; the flag is tested with a `u32` comparison, never a
  bitwise mask (A7: masks cost 57 steps per iteration against 14 in felt);
* `child0` is the **front** side (`geom2d::SIDE_FRONT`, what `R_PointOnSide`
  numbers 0) and `child1` the back one; a point exactly on a partition goes
  to the back child, the same tie-break as everywhere else in the stack;
* `cross_bsp` visits subsectors in order of increasing distance from `p1`
  (tested: the first one visited always contains `p1`, and reversing the
  trace reverses the whole visit order);
* both walks **terminate on malformed data**: they panic (`'bsp: cycle or
  oob'`) after more hops, or more recursion depth, than there are nodes,
  instead of looping forever.

## The descent is the expensive part, and that is structural

S1 §5.5/§5.6 found `point_in_subsector` to be **35 % of an optimized tic**
on E1M1 (1 014 steps for ~10 levels). This crate measures **105 steps per
level** over its 63-node test tree, i.e. exactly the same per-level cost, and
the breakdown says why: **4 `Span` reads per level at 14 steps each** (three
coefficients plus one child) against a single 11-step comparison. Hoisting
the point's `geom2d` term out of the loop — which this crate does — saves
only 3 steps per level.

So there is no cheaper descent to write. The way out is **not to descend**:
R2-A9's "blockmap cell → subsector candidates" accelerator answers in one
read plus one or two convex tests, and `blockmap::PackedLists` is the shape
it is consumed as. This crate stays as the fallback and as the ground truth
the accelerator is checked against.

S1 §7 also warns that a *partial* accelerator is worse than none (the
"uniform cell" shortcut cost 520 steps/tic more than it saved, because the
test that fails is paid every time). Any consumer adding a fast path must
measure it on a real path, not on the favourable case.

## Measured step costs

`bench/` is a standalone Scarb package; `bench/measure.py` is the crate's
**step-budget test** (fails at +10 % over `bench/budgets.json`). Costs are
net of the baseline op that builds the same operands, over the same 63-node
tree as the tests (`bench/src/tree.cairo`, regenerated by the same script).

```sh
cd bench && python3 measure.py          # measure + check budgets
python3 measure.py --update             # re-baseline after an intended change
```

| Operation | steps (net) | range checks | note |
|---|---:|---:|---|
| `is_subsector` + `subsector_of` | 18 | 3 | the two together |
| `trace` | 12 | 0 | two `geom2d::hoist` |
| `child_box` | 96 | 11 | four `Span` reads |
| `point_in_subsector` (6 levels) | 631 | 42 | **105 per level** |
| `cross_bsp`, full crossing | 2 016 | 159 | 4 subsectors, 7 nodes descended twice |
| `cross_bsp`, stopped at the first | 642 | 44 | the blocked-sight case |

Bytecode: **7 466 words** for the benchmark executable, which includes the
63-node tree (882 felts) and `geom2d`/`bam`/`fixed`.

The gap between a full crossing (2 016) and a stopped one (642) is why the
visitor returns a `bool`: `P_CheckSight` answers "blocked" without walking
the rest of the ray.

## Tests

`scarb test -p bsp` — 10 unit tests + 2 integration tests, over a generated
63-node / 64-leaf tree (`scripts/gen_vectors.py`, which also writes the
benchmark's copy of the tree):

* **reference values**: 1 000 points with the subsector Doom's
  `R_PointInSubsector` reaches — 142 of them land **exactly on a partition
  line**, the tie this crate resolves toward the back child — and 200 traces
  with the full ordered list of subsectors `P_CrossBSPNode` visits (2 295
  visits in all, the longest trace crossing 55 subsectors). Both
  expectations come from a Python transcription of Doom's algorithms over
  the same exact integer predicate the crate uses.
* **properties**: the first subsector a traversal visits is the one
  containing the ray's origin; reversing a trace reverses the visit order
  exactly; the box stored for the chosen child contains the point at every
  descent.
* **edge cases**: a degenerate trace (both endpoints equal) visits exactly
  one subsector; a trace whose endpoints lie on partition lines still
  terminates; a cyclic tree panics instead of hanging; the child-id
  encoding at its boundaries.

The integration target (`tests/lib.cairo`) covers only the loop-free part of
the API: `scarb test` computes gas for that target even though the workspace
disables gas, and both the descent (a `while`) and the traversal (a
recursion) are lowered to recursive functions, whose cost computation then
fails. The unit-test target has no such restriction.

`cairo-coverage` (0.5.0, installed via asdf) was **not** run: it consumes
`snforge test --save-trace-data` traces and this workspace's runner is
`scarb cairo-test`. Coverage is argued instead: the 1 000 points and 200
traces reach both children at every level, both outcomes of the
`SIDE_CROSS` fold, the early-stop and run-to-completion paths of
`cross_bsp`, and the panic guard.
