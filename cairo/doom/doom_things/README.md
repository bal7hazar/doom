# doom_things

**Does**: owns Doom's *thing* data for everything Freedoom E1M1 can spawn —
`mobjinfo` (48 entries, 18 fields each), the `info.c` state machine (266
states as the five `fsm::StateTables` columns), `d_items.c`'s weapon chains,
the `doomednum` → kind lookup and `m_random.c`'s 256-byte `rndtable` — and
the typed lookups over them (`thing_info`, `spawn_state`, `flags`,
`kind_of_doomednum`, `states`, `rndtable`, `weapon_states`). The numbers are
generated by `scripts/gen_things.py` from a local copy of linuxdoom-1.10's
tables into `src/tables.cairo`; the client's half (sprite names per state and
per `doomednum`) is written to `generated/sprites.json`.

**Does not**: run the state machine (`fsm`), draw from the table (`prng`),
or implement a single action — `A_Chase`, `A_PosAttack` and the rest belong
to `doom_monsters` and `doom_player`. It holds no per-instance state: a
mobj's position, health and current state live in `doom_game`'s `GameState`,
exactly as `mobjinfo_t` is shared by all instances in the original. It knows
nothing about a map (`doom_map`) and carries no sounds.

**Invariants**:

* row 0 is `S_NULL`: action `fsm::NO_ACTION`, `fsm::FOREVER` tics, pointing
  at itself — which is what lets `fsm` reserve action id 0;
* `fsm::validate` passes, every `next_state` and every `mobjinfo` state field
  is in range, and every action id is below `NUM_ACTIONS`;
* **every chain either terminates or loops**: from each of the 266 states,
  Floyd's cycle detection reaches a `FOREVER` state or a cycle — so no walk
  runs off the table and none can advance for ever without repeating;
* the longest run of zero-tic states is [`MAX_ZERO_TIC_CHAIN`] = 1, so the
  bounded `while tics_left == 0` loop D15 asks for is enough;
* `DOOMEDNUM_KEYS` is sorted and unique (the binary search depends on it) and
  every placeable kind round-trips through `kind_of_doomednum`;
* every value is a `u32` or a `Fixed` below 2^33 — far under the 2^72
  threshold of A7.

## Action ids replace function pointers

Cairo has no function pointers, so a state cannot carry `A_Chase`. It carries
an **action id** instead: `fsm::advance` returns the id of the state it
entered and the caller dispatches on it (D15). The ids are `const`s in
[`tables`] — `A_CHASE`, `A_LOOK`, `A_POSATTACK`, … — and
`generated/actions.md` is the same table in prose, for `doom_monsters` and
`doom_player` to implement against. **`0` is `fsm::NO_ACTION`**; this roster
uses 25 actions:

| group | actions |
|---|---|
| monster AI | `A_LOOK`, `A_CHASE`, `A_FACETARGET` |
| monster attacks | `A_POSATTACK` (zombieman), `A_SPOSATTACK` (shotgun guy), `A_TROOPATTACK` (imp, melee and fireball), `A_SARGATTACK` (demon/spectre) |
| damage and death | `A_PAIN`, `A_SCREAM`, `A_XSCREAM`, `A_PLAYERSCREAM`, `A_FALL`, `A_EXPLODE` (the barrel) |
| weapons | `A_WEAPONREADY`, `A_RAISE`, `A_LOWER`, `A_REFIRE`, `A_PUNCH`, `A_SAW`, `A_FIREPISTOL`, `A_FIRESHOTGUN`, `A_FIRECGUN` |
| muzzle flash | `A_LIGHT0`, `A_LIGHT1`, `A_LIGHT2` |

Anything outside this list is not reachable on E1M1 and is not generated.

## The roster

The generator takes every `doomednum` that appears in the map's THINGS lump
**at any skill** (48 `mobjinfo` entries out of Doom's 137) plus the entries
nothing places but everything needs: `MT_PLAYER`, `MT_TROOPSHOT` (the imp's
fireball), `MT_PUFF`, `MT_BLOOD`, and the two items `P_KillMobj` drops —
`MT_CLIP` for a zombieman and `MT_SHOTGUN` for a shotgun guy. The whole-map
roster rather than only the skill-2 subset costs ~200 words and keeps the
crate valid if D3's skill choice is revisited.

Two facts the skill-2 filter turns up, both worth knowing before
`doom_player` is written:

* **the only weapon *pickup* reachable at skill 2 is the chainsaw.** The
  shotgun, chaingun, rocket launcher and plasma rifle on E1M1 are all either
  `easy`-only or `MTF_NOTSINGLE`. A single-player skill-2 run therefore
  starts with fist + pistol and gets a shotgun only by killing a shotgun guy;
* **the spectre never spawns at skill 2** (its one placement is
  `hard+ambush`), though its `mobjinfo` is generated anyway — it shares every
  state with the demon and differs only by `MF_SHADOW` and one row.

## `P_Random` counts before it reads

Doom's `P_Random` is `prndindex = (prndindex + 1) & 0xff; return
rndtable[prndindex]`, while `prng::next` reads `table[index]` *then*
advances. Starting a run at `prng::from_index(1)` reproduces Doom's own
sequence (`8, 109, 220, …`); `prng::new()` would start one byte early, at
`rndtable[0] = 0`. `doom_game::genesis` should seed both RNG streams at 1.

## Measured step costs

`bench/` is a standalone Scarb package; `bench/measure.py` is the crate's
**step-budget and bytecode-budget test** (+10 % over `bench/budgets.json`, or
above 6 000 words of tables, fails).

```sh
cd bench && python3 measure.py          # measure + check budgets
python3 measure.py --update             # re-baseline after an intended change
```

| Operation | steps (net) | range checks | note |
|---|---:|---:|---|
| `spawn_state` / `flags` | 12 | 1 | one `Span` read — this crate has no `@LevelMap`-style snapshot to pay for |
| `prng::next` over `rndtable` | 18 | 1 | `prng`'s own floor |
| `fsm::enter` | 32 | 3 | two reads |
| `fsm::advance` | 33 | 2 | averaged over a real 4-tic cycle |
| `weapon_states` | 36 | 4 | five reads |
| `kind_of_doomednum` | 214 | 31 | 6 binary-search steps; called once per thing at genesis, never in a tic |
| `thing_info` (18 fields) | 225 | 17 | cold path; hot callers read the one field they need |

### Bytecode

| Array | Words |
|---|---:|
| `STATE_SPRITE`/`FRAME`/`TICS`/`ACTION`/`NEXT` (266 each) | 1 330 |
| `MI_*`, 18 columns × 48 kinds | 864 |
| `RNDTABLE` | 256 |
| `DOOMEDNUM_KEYS` + `DOOMEDNUM_KINDS` | 88 |
| `WEAPON_*`, 5 × 5 | 25 |
| scalars (`NUM_STATES`, `NUM_KINDS`, `NUM_ACTIONS`) | 3 |
| **Total (analytic)** | **2 566** |
| **Measured** (`bench/size` − `bench/baseline`) | **3 410** |

The 844-word gap is the fixed `span()` glue Cairo emits per `const` array
(~35 words each, measured on a synthetic array: an empty program is 112
words, one with a 1 000-element array is 1 147). At 3 410 words the tables
cost **52 467 steps of bootloader program-hashing per proof segment**, well
inside the 6 000-word slice of docs/G0.md D4's 20 000 for data — and the
whole `doom_map` + `doom_things` data comes to 21 722 words, which is the
number P1.6 has to work against.

## Regenerating

```sh
cd /tmp
for f in info.h info.c m_random.c d_items.c; do
  curl -sSO https://raw.githubusercontent.com/id-Software/DOOM/master/linuxdoom-1.10/$f
done
python3 cairo/doom/doom_things/scripts/gen_things.py \
    --src /tmp --level /tmp/wadout/e1m1.json --write
```

The C sources are **never committed** (the same rule as the WAD). The
generator parses the upstream tables and re-emits the *numbers* in this
project's layout with compacted ids; no C code is reproduced. It prints the
word table, writes `bench/manifest.json` for `measure.py` to cross-check
against the compiled size, and runs `scarb fmt`.

## Tests

`scarb test -p doom_things` — **19 tests**:

* **shape**: `fsm::validate` passes; 266 states, 48 kinds, 26 action ids;
  every column is the same length; row 0 is `S_NULL`;
* **reachability**: every referenced state and action exists, and every
  `mobjinfo` state field is in range;
* **termination**: Floyd's cycle detection from all 266 states — each chain
  either reaches a `FOREVER` state or loops; 3 zero-tic states, longest run 1;
* **vanilla chains**, spot-checked against `info.c`: the zombieman's idle
  pair (10 tics, `A_LOOK`, two states), its 8-frame 4-tic `A_CHASE` loop, its
  attack (`A_FACETARGET` 10 → `A_POSATTACK` 8 → 8 idle → chase), its pain
  (silent frame → `A_PAIN` → chase, painchance 200), its death
  (`A_SCREAM`, `A_FALL`, `FOREVER` corpse) and gib death (`A_XSCREAM`,
  `A_FALL`, 9 frames);
* **`mobjinfo` spot values** for the zombieman, shotgun guy, imp, demon and
  spectre (which shares the demon's states and adds `MF_SHADOW`), the imp's
  fireball (damage 3, speed `10 × FRACUNIT`, `MF_MISSILE|MF_NOGRAVITY`), the
  puff, the blood and the barrel (`A_EXPLODE` on its fourth death frame);
  every monster is `MF_SOLID|MF_SHOOTABLE|MF_COUNTKILL`;
* **lookup**: all 44 placeable kinds round-trip, player and deathmatch starts
  and unknown types return `None`, and the key array is sorted;
* **weapons**: all five chains in range, only the fist has no flash,
  `A_PUNCH`/`A_FIREPISTOL`/`A_FIRECGUN` on the right frames;
* **RNG**: 256 entries, checksum 32 986, spot values, `prng::is_valid_table`,
  and that `from_index(1)` reproduces Doom's `P_Random` order;
* **transitional agreement**: the compat catalogue's health/radius/height
  match the generated entry for the same Doom type;
* **provability**: every `Fixed` stays below 2^33.

## Coverage

`python3 bench/coverage.py` measures line coverage with `cairo-coverage`
0.5.0: **19 tests, 53/53 production lines = 100 %**. Unlike `doom_map`, this
crate's 2 566 felts of tables compile under the `inlining-strategy = "avoid"`
that coverage requires, so the real tests run against the real data. Lines at
or below an inline `#[cfg(test)]` marker are excluded, as are the generated
`src/tables.cairo` (data, not code) and `src/tests.cairo`.

`cairo-coverage` 0.5.0 emits no `BRF`/`BRH` records, so **branch** coverage
cannot be reported by the tool; line coverage is the proxy, and since
`scarb fmt` puts every branch arm on its own line, a missed arm shows up as a
missed line. On top of the figure: the tests reach both outcomes of
`kind_of_doomednum` (found and not found, and both sides of the binary
search), all five `weapon_states` arms, all three `compat` variants, and both
the terminating and looping verdicts of the chain walk.

## Transitional

`src/compat.cairo` still exports the Phase-0 skeleton's three-variant
`MobjType`, `MobjInfo` and `info_of`, re-exported at the crate root, because
`doom_physics`, `doom_player`, `doom_monsters` and `doom_game` still import
them. `compat::kind_of` maps each variant to its generated `KIND_*` index so
the tests can keep the two from drifting. This is the `doom_things` half of
the D17 clean-up and disappears with P1.6.
