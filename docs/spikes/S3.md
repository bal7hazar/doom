# S3 — Exécution temps réel d'un `step_tic` Cairo dans un Worker

Action de risque **R5-A1** (et préparation de **R5-A2**).
Décision **A1** (PLAN.md §1), tâche 3 de la phase 2 (PLAN.md §2), ligne S3 de
l'orchestration (ROADMAP.md §5).

Code : [`prover/sim/`](../../prover/sim) — voir son
[README](../../prover/sim/README.md) pour l'API et les commandes.
Mesures brutes : `prover/sim/bench/results/*.json`.

---

## 1. Question

> Peut-on exécuter le programme Cairo `step_tic` **≥ 100 tics/s de façon
> soutenue, à 4 000 steps/tic, dans un Worker de navigateur** ?

Critère de sortie de R5-A1. Le budget d'un tic à 35 Hz est de **28,6 ms** ;
100 tics/s (10 ms/tic) laisse une marge de 3× pour le rendu, les entrées et le
prouveur en tâche de fond (R6-A1).

Sous-questions :

* que faut-il reconstruire à chaque tic, et que peut-on mettre en cache une
  fois pour toutes ?
* combien coûte l'alternative naïve (re-parser l'`.executable.json` à chaque
  appel, comme le fait `execute` de `stwo-cairo-ts`) ?
* le coût de (dé)sérialisation de ~1 500 felts et le passage JS↔wasm sont-ils
  significatifs ?
* la consommation mémoire est-elle stable sur une partie entière ?

## 3. Méthode

### 3.1 Le wrapper `hellproof-sim`

Crate `cdylib` + `rlib` compilée pour `wasm32-unknown-unknown` (exécution
seule : pas de trace, donc pas besoin de Memory64 ni de wasm64 — c'est S2 qui
en a besoin pour le prouveur).

API wasm-bindgen :

* `SimProgram.load(executable_json)` — parse l'`.executable.json` **une fois** ;
* `SimProgram.run(args: Uint8Array) -> Uint8Array` — un tic ;
* `SimProgram.reserve_input(n) / run_buffered(n) / output_ptr()` — variante
  **sans copie**, les arguments sont écrits directement dans la mémoire
  linéaire wasm ;
* `run_json(...)` — aide au débogage uniquement ;
* `run_once_from_json(...)` — l'alternative naïve, présente *uniquement* pour
  être mesurée ;
* `wasm_memory_bytes()` — taille de la mémoire linéaire (contrôle de fuite).

**Encodage des felts, sans JSON** : chaque felt est une valeur **little-endian
de 32 octets fixes** dans un `Uint8Array` ; le felt `i` occupe les octets
`[32i, 32i+32)`, octet de poids faible en premier, complété de zéros, et doit
être canonique (`< p`) — un felt non canonique est **rejeté** au lieu d'être
réduit silencieusement, pour qu'un bug JS ne puisse pas modifier la simulation
en silence. Un état de 1 500 felts fait donc exactement 48 000 octets.

Le tampon d'arguments est la **sérialisation Cairo** des paramètres du point
d'entrée (ce que prend `scarb execute --arguments`) : pour
`fn step_tic(state: Array<felt252>, cmd: felt252)`, c'est
`[len, s0, …, s_{len-1}, cmd]`. La sortie est la sérialisation Cairo de la
valeur de retour, c'est-à-dire littéralement le contenu du segment du builtin
`output` : `[len, e0, …]`. Un `panic` Cairo remonte comme une **erreur**,
jamais comme une valeur (le code d'entrée finit par `assert 0 = panic_flag`, et
le wrapper rattache la charge utile du panic déposée par le hint `AddMarker`).

### 3.2 Ce qui est mis en cache / reconstruit

| Mis en cache dans `SimProgram` (une fois) | Pourquoi c'est possible |
|---|---|
| `Executable` désérialisé → `cairo_vm::types::program::Program` | cairo-vm garde `SharedProgramData` (bytecode + collection de hints) derrière un `Arc` : cloner un `Program` à chaque appel est en `O(1)` |
| la table `string_to_hint` | ne dépend que du programme |
| une instance de `CairoHintProcessor` | **réinitialisée** entre les appels (arguments, markers, traceback, run resources) au lieu d'être reconstruite |
| point d'entrée, builtins, configuration de run | idem |
| les tampons de travail arguments/sortie | évite deux allocations par tic |

| Reconstruit à **chaque** appel | Pourquoi c'est inévitable |
|---|---|
| `CairoRunner` + la `VirtualMachine` qu'il possède (segments mémoire, builtin runners, exec scopes) | cairo-vm 3.2 n'expose aucune API de remise à zéro, et la mémoire d'un run terminé n'est pas réutilisable |
| les arguments utilisateur (`Vec<Arg>`) | ils portent les felts d'entrée du tic |
| le chargement du bytecode dans le segment programme | fait par `CairoRunner::initialize` — **coût proportionnel à la taille du programme**, cf. §4.6 |

Deux modes de run sont implémentés et comparés : `Execution` (point d'entrée
`Bootloader`, hors proof mode — c'est le mode de la simulation) et
`ProofShapeNoTrace` (point d'entrée `Standalone`, initialisation proof mode
identique à celle du prouveur, mais trace, relocation mémoire, bouchage de
trous et finalisation de segments désactivés).

### 3.3 Le programme de référence `bench/step_tic/`

`#[executable] fn step_tic(state: Array<felt252>, cmd: felt252) -> Array<felt252>` :
arithmétique `felt252` pure qui **lit et réécrit chaque élément de l'état**,
avec une dépendance de données entre éléments consécutifs (rien n'est
éliminable).

Calibration au `scarb execute --print-resource-usage` (Scarb 2.19.4,
`enable-gas = false`) :

| mesure | steps / felt d'état |
|---|---|
| désérialisation `Serde` de l'argument `Array<felt252>` | 12,0 |
| sérialisation `Serde` de la valeur de retour | 10,0 |
| la boucle de mixage elle-même | 13,0 |
| **total** | **35,0** |

soit `steps(n) = 35 n + 69`, linéaire et parfaitement prévisible. **Le nombre
de steps est donc piloté par la longueur de l'état**, et c'est lui qui
sélectionne le budget demandé :

| cas | felts d'état | steps/tic (mode exécution) | charge utile in |
|---|---:|---:|---:|
| `4k` | 112 | **3 986** | 3 648 o |
| `10k` | 284 | **10 006** | 9 152 o |
| `full-1500` | 1 500 | **52 566** | 48 064 o |

> **Constat important pour R5 et S1.** L'énoncé de R5 (« 1 500 felts d'état,
> ~4 000 steps/tic ») est **incompatible** avec le `Serde` de Cairo 2 : la
> seule enveloppe entrée+sortie d'un `Array<felt252>` de 1 500 éléments coûte
> **~33 000 steps**, avant tout calcul. Mesures de contrôle (état de 1 500
> felts) : point d'entrée qui ignore l'état, 18 041 steps ; point d'entrée qui
> renvoie l'état inchangé, 33 052 steps ; boucle de lecture seule sans tableau
> de sortie, 31 551 steps. Le plancher d'un aller-retour de 1 500 felts est
> donc de l'ordre de 5 × 10⁴ steps, soit 13× le budget supposé. Voir §6.3.

Le benchmark mesure donc les trois cas : `4k` répond littéralement au critère
de R5-A1, `full-1500` répond à la question réaliste « et avec un état de la
taille d'un état Doom ? ».

Un second exécutable, `step_tic_rounds`, ajoute un bouton de calcul
(`rounds`, ~9,4 steps/felt/round) pour augmenter le nombre de steps **à charge
utile constante** ; il n'est pas utilisé dans les tableaux ci-dessous mais sert
à séparer coût de calcul et coût de transfert.

### 3.4 Les trois environnements

Le **même corps de benchmark** (`bench/bench-core.mjs`) est importé tel quel
par le runner Node et par le Worker du navigateur ; le binaire natif
(`src/bin/bench.rs`) emprunte le même chemin de code Rust.

* **natif** : `target/release/hellproof-sim-bench`, un processus par cas ;
* **Node (wasm)** : même artefact `pkg/hellproof_sim_bg.wasm` que le navigateur ;
* **Chromium (wasm)** : page servie par `bench/server.mjs` avec les en-têtes
  **COOP/COEP** (isolation cross-origin, donc `performance.now()` non
  dégradé et `SharedArrayBuffer` disponible), benchmark exécuté **dans un
  `Worker` de type module**, piloté par Playwright headless.

Protocole par cas : 500 appels de chauffe (le wasm passe de Liftoff à TurboFan
en arrière-plan), puis **2 000 appels consécutifs** chronométrés un par un ;
passe séparée de 300 appels pour la ventilation interne (la lecture des
compteurs ne pollue pas la mesure de débit) ; 500 appels pour la variante sans
copie ; 10 000 appels pour la mémoire.

Le tampon d'arguments est alloué **une fois** et rempli sur place. En allouant
un `Uint8Array` neuf par tic, la moyenne double et le p99 est multiplié par 20
(pression GC) : c'est une mesure de GC, pas de VM — et le client gardera de
toute façon l'état dans un tampon unique (R5-A2).

Chaque run publie une **empreinte FNV-1a des octets de sortie de 100 tics
consécutifs**, comparée entre les trois environnements (amorce de R5-A3).

## 4. Résultats

### 4.1 Débit soutenu (2 000 appels consécutifs)

| cas | felts d'état | steps/tic | natif tics/s | Node tics/s | **Worker Chromium tics/s** | steps/s Chromium | sorties identiques |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | :---: |
| `4k` | 112 | 3 986 | 4 642 | 1 981 | **2 289** | 9,12 M | oui |
| `10k` | 284 | 10 006 | 1 921 | 828 | **936** | 9,37 M | oui |
| `full-1500` | 1 500 | 52 566 | 366 | 146 | **179** | 9,43 M | oui |

* Le Worker Chromium soutient **2 289 tics/s à 4 000 steps/tic**, soit **23×**
  le critère de R5-A1 et **65×** le besoin réel de 35 Hz.
* Le débit en steps est quasi constant (**≈ 9,1–9,4 M steps/s**) : le coût est
  linéaire en steps, pas en taille d'état. cairo-vm en wasm tourne donc à
  ~9 M steps/s sur ce cœur, soit **2,2× plus lent que natif** (~19 M steps/s).
  C'est très au-dessus de l'hypothèse de CONTEXT/RISKS (0,5–2 M steps/s).
* Chromium est **10–20 % plus rapide que Node** sur le même artefact.
* Même un tic de **52 566 steps** (état Doom complet de 1 500 felts) tient
  **179 tics/s**, soit 5,6 ms sur les 28,6 ms du budget.
* Les empreintes de sortie natif / Node / Chromium sont **identiques** sur les
  trois cas.

### 4.2 Ventilation par appel, Worker Chromium (ms)

| cas | remplissage args (JS) | copie JS→wasm | décodage felts | init runner+VM | **run VM** | lecture sortie | encodage sortie | total appel |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `4k` | 0,0009 | 0,0013 | 0,0088 | 0,0030 | **0,4123** | 0,0019 | 0,0022 | 0,4356 |
| `10k` | 0,0012 | 0,0014 | 0,0225 | 0,0028 | **1,0232** | 0,0044 | 0,0046 | 1,0663 |
| `full-1500` | 0,0055 | 0,0025 | 0,1160 | 0,0046 | **5,3964** | 0,0203 | 0,0225 | 5,5696 |

**≥ 94 % du temps est dans la VM** dans tous les cas. Tout le reste —
sérialisation des arguments côté JS, copie JS↔wasm, décodage des 1 502 felts
little-endian, construction du `CairoRunner` et de la VM, relecture du segment
de sortie, réencodage — pèse **0,023 ms à 4 k steps** et **0,17 ms** même avec
un état de 1 500 felts. La reconstruction du runner à chaque tic, qui était
l'inconnue principale de R5, coûte **3 à 5 µs**.

Pour référence, natif (même ventilation, cas `4k` / `full-1500`) :
`run VM` 0,2078 / 2,6636 ms, `init runner` 0,0017 / 0,0023 ms,
décodage 0,0021 / 0,0268 ms.

### 4.3 Distribution des latences, Worker Chromium (ms)

| cas | p50 | p95 | p99 | max | appels > 28,6 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| `4k` | 0,430 | 0,465 | 0,505 | 0,715 | **0** |
| `10k` | 1,060 | 1,120 | 1,165 | 1,245 | **0** |
| `full-1500` | 5,570 | 5,745 | 5,820 | 6,110 | **0** |

Aucun appel, sur 2 000, ne dépasse le budget d'un tic. Le rapport max/p50 est
de 1,7 dans le pire cas : pas de « pause » périodique, pas d'effet d'escalier
de l'allocateur.

### 4.4 Copie JS↔wasm : API copiante vs sans copie

| cas | charge utile | `run(Uint8Array)` | `run_buffered` (sans copie) | écart |
| --- | ---: | ---: | ---: | ---: |
| `4k` | 3 648 o | 0,4356 | 0,4308 | 0,0048 |
| `10k` | 9 152 o | 1,0663 | 1,0580 | 0,0083 |
| `full-1500` | 48 064 o | 5,5696 | 5,5889 | −0,0193 |

La copie n'est pas mesurable : écrire 48 ko dans la mémoire linéaire coûte
**0,0025 ms**. C'est déjà la réponse au critère de sortie de **R5-A2**
(« coût de transfert < 1 ms/tic ») : on en est à **1/400** du budget. La
variante sans copie reste utile pour éviter d'allouer un `Uint8Array` par tic
(pression GC), pas pour la copie elle-même.

### 4.5 Latence du premier appel

| environnement | fetch wasm | instanciation wasm | parse de l'exécutable | premier run |
| --- | ---: | ---: | ---: | ---: |
| natif | — | — | 1,24 ms | 0,99 ms |
| Node | — | — | 7,74 ms | 7,07 ms |
| **Worker Chromium** | 22,4 ms | 9,2 ms | 7,11 ms | 4,79 ms |

Démarrage à froid du Worker : **≈ 44 ms** en local, dont 22 ms de
téléchargement (localhost) et 9 ms d'instanciation d'un module de 12,6 Mo
(compilation paresseuse de Chromium). Le premier run coûte 10× un run chaud
(compilation Liftoff des fonctions chaudes), et le régime stable est atteint en
quelques centaines d'appels. Sans conséquence : c'est un coût d'écran de
chargement.

### 4.6 L'alternative naïve : re-parser l'`.executable.json` à chaque appel

Le programme de référence est minuscule (200 mots de bytecode, 5 hints,
4 131 octets de JSON) : la comparaison directe y est peu parlante. On fait donc
grossir le bytecode avec des mots morts (`--inflate`) pour mesurer la pente.

| mots morts ajoutés | JSON (octets) | parse (ms) | appel avec cache (ms) | appel naïf (ms) | rapport |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0 | 4 131 | 0,13 | 0,219 | 0,279 | 1,3× |
| 5 000 | 42 781 | 0,91 | 0,249 | 1,033 | 4,2× |
| 20 000 | 158 731 | 3,15 | 0,335 | 3,289 | 9,8× |
| 100 000 | 777 671 | 16,17 | 0,834 | 14,869 | 17,8× |

Dans le Worker Chromium, sur le programme de 4 ko : 0,436 ms avec cache contre
0,582 ms en naïf (1,3×).

Deux enseignements :

1. **Le gain du cache croît linéairement avec la taille du programme.** Pour un
   `step_tic` réaliste (de l'ordre de 10⁵ mots de bytecode), re-parser à chaque
   tic coûterait **~15 ms/tic**, soit la moitié du budget de 28,6 ms, pour
   zéro travail utile. C'est exactement le piège de `execute` dans
   `stwo-cairo-ts`, et R5-A1 l'évite.
2. **Le coût par appel croît lui aussi avec la taille du programme**
   (0,219 → 0,834 ms), parce que `CairoRunner::initialize` recopie *tout* le
   bytecode dans le segment programme à chaque run. À 10⁵ mots, c'est ~0,6 ms
   par tic de recopie pure. Voir le suivi §6.2.

Autres comparaisons (natif, cas `4k`) :

| variante | ms/appel |
|---|---:|
| référence (processeur de hints réutilisé, mode exécution) | 0,2154 |
| processeur de hints reconstruit à chaque appel | 0,2089 |
| mode « forme preuve » (point d'entrée `Standalone`, proof mode, sans trace) | 0,2132 |

La réutilisation du processeur de hints n'apporte rien **sur ce programme**
(5 hints) ; elle deviendra mesurable sur un programme qui en compte des
centaines, et elle ne coûte rien. Surtout : **le mode « forme preuve » coûte le
même prix que le mode exécution**, ce qui veut dire qu'on peut faire tourner la
simulation temps réel exactement dans la configuration d'initialisation du
prouveur si R5-A3 l'exige, sans pénalité.

### 4.7 Mémoire sur 10 000 appels

| environnement | mémoire avant | après | croissance |
| --- | ---: | ---: | ---: |
| Node (mémoire linéaire wasm) | 6 619 136 | 6 619 136 | **0** |
| Worker Chromium (mémoire linéaire wasm) | 6 619 136 | 6 619 136 | **0** |
| natif (octets vivants dans l'allocateur) | 92 180 | 92 180 | **0** |

Aucune croissance sur 10 000 tics (≈ 4,8 minutes de jeu à 35 Hz), ni côté wasm
ni côté allocateur Rust (le binaire natif est instrumenté par un
`GlobalAlloc` compteur). Le débit soutenu sur ces 10 000 appels (2 172 tics/s
dans Chromium) est identique à celui mesuré sur 2 000 : **pas de dégradation**.

La mémoire linéaire wasm plafonne à **6,6 Mo** pour le cas `4k`
(≈ 0,5 Mo de plus pour l'état de 1 500 felts) : la simulation ne consomme donc
presque rien face au prouveur (S2) et **n'a pas besoin de Memory64**.

`performance.memory` n'existe pas dans un Worker et
`performance.measureUserAgentSpecificMemory()` n'était pas exposé dans ce
contexte ; la taille de la mémoire linéaire wasm — la seule qui puisse croître
sans jamais redescendre — est la mesure pertinente et elle est plate.

## 5. Verdict

> ## **GO**
>
> Le critère de sortie de R5-A1 — *« ≥ 100 tics/s soutenus sur 4 k steps/tic,
> mesuré dans un Worker »* — est atteint avec **2 289 tics/s**, soit **23× la
> cible**, sans aucun appel au-dessus du budget de tic sur 2 000 appels, sans
> croissance mémoire sur 10 000 appels, et avec des sorties identiques bit à
> bit entre natif, Node et Chromium.
>
> Le critère est également atteint **avec un état de 1 500 felts et 52 566
> steps/tic** (179 tics/s, 5,6 ms des 28,6 ms disponibles), c'est-à-dire dans
> l'hypothèse réaliste, pas seulement dans l'hypothèse nominale.

Conséquences :

* **La décision A1 est confirmée** : Cairo peut être la source de vérité de la
  simulation *y compris en temps réel*. Le port TypeScript parallèle n'est pas
  nécessaire.
* **Le repli R5-A4 (miroir TypeScript, +15 jp, risque de divergence permanent)
  n'est pas activé** et doit être retiré du chemin. Il n'y a aucune raison
  d'assumer 15 jours-personnes et un risque de désynchronisation permanent pour
  un facteur 23 de marge. Si un navigateur particulier devait s'avérer 10× plus
  lent que Chromium (non mesuré à ce stade, cf. §6.7), la marge resterait
  suffisante.
* **R5-A2 a déjà sa réponse partielle** : le transfert d'un état de 48 ko coûte
  0,0025 ms, très en deçà du critère « < 1 ms/tic ». Le `SharedArrayBuffer`
  reste souhaitable pour éviter la pression GC et pour le rendu interpolé, pas
  pour le coût de copie.

Réserves, aucune bloquante :

1. **Taille de l'artefact wasm : 12,6 Mo (2,0 Mo en brotli).** Acceptable pour
   un spike, pas pour la page de jeu ; cf. §6.1.
2. **Le programme de référence est petit.** Le coût par tic croît avec la
   taille du bytecode (§4.6, point 2) ; à 10⁵ mots, il faut compter ~0,6 ms de
   recopie du programme par tic en plus des steps. La marge absorbe largement,
   mais le suivi §6.2 est à faire avant la phase 2.
3. **Mesuré sur Chromium seulement**, sur un M2 Max. Voir §6.7.

## 6. Suites

### 6.1 Réduire l'artefact wasm (12,6 Mo → cible < 3 Mo brut)

`cairo-lang-executable` n'est utilisé que pour **désérialiser** la structure
`Executable`, mais il dépend de `cairo-lang-compiler`, `cairo-lang-lowering`,
`cairo-lang-sierra-to-casm` et de salsa ; `cairo-lang-runner` tire en plus
`cairo-lang-starknet` et les courbes `ark-*`. Pistes, par ordre de rendement :

* remplacer `Executable` par un miroir `serde` local (`AssembledCairoProgram`
  de `cairo-lang-casm` + les points d'entrée) : supprime tout le compilateur ;
* remplacer `CairoHintProcessor` par un processeur de hints restreint aux hints
  réellement émis par le programme (les 5 du benchmark ; quelques dizaines pour
  un vrai programme), ce qui supprime `cairo-lang-starknet` et les syscalls ;
* `wasm-opt -Oz`, et servir le `.wasm` en brotli (déjà 2,0 Mo) ;
* format binaire pré-parsé pour le programme, à la place du JSON (supprime
  aussi les 7 ms de parse au démarrage).

### 6.2 Faire partager le segment programme entre les runs (cairo-vm)

`CairoRunner::initialize` recopie tout le bytecode dans un segment mémoire
neuf à chaque run — d'où la croissance du coût par appel avec la taille du
programme (§4.6). Deux options : construire une fois la mémoire initiale et la
cloner (moins cher qu'un remplissage), ou proposer en amont à cairo-vm un
segment programme partageable en lecture seule. À chiffrer sur le vrai
`step_tic` dès que S1 en produit un.

### 6.3 Revoir l'hypothèse « 1 500 felts / 4 000 steps » (pour S1 et le cœur de jeu)

Le `Serde` d'un `Array<felt252>` coûte **22 steps par felt** en aller-retour,
et la boucle qui les touche ~13 de plus. Un état de 1 500 felts passé en
argument et rendu en retour, c'est **~50 000 steps par tic incompressibles**,
qui sont aussi **50 000 steps à prouver** — l'impact est donc bien plus fort
sur R1/R2 (coût de preuve) que sur R5 (temps réel), où la marge est confortable.
Pistes à instruire avec S1 :

* **empaqueter l'état** (plusieurs champs par felt) : le coût `Serde` est par
  felt, pas par bit ;
* ne faire transiter que le **delta** de l'état et garder le reste implicite ;
* exposer l'état comme un segment dédié plutôt que comme un `Array<felt252>`
  sérialisé, si le format d'exécutable le permet.

### 6.4 Étendre l'équivalence (R5-A3)

L'empreinte FNV-1a sur 100 tics est en place et concorde entre les trois
environnements. À généraliser : rejouer les 20 replays du corpus (a) par
`step_tic` en boucle dans le Worker, (b) par `run_segment` natif, (c) par
l'exécution du prouveur, et comparer les hashes en CI.

### 6.5 Réutiliser le runner (gain potentiel faible)

Un `CairoRunner::reset` en amont de cairo-vm économiserait les 3–5 µs d'init

## 7. Esquisse de l'architecture Worker (R5-A2)

Non implémentée dans ce spike ; à réaliser en phase 2. Les chiffres du §4 la
dimensionnent.

### 7.1 Vue d'ensemble

```
  thread principal                         Worker « sim »
  ─────────────────                        ───────────────
  clavier/souris ──► ring d'entrées ──────► scheduler 35 Hz
                     (SAB, Atomics)          │
                                             ├─ fillArgs(state, ticcmd)
                                             ├─ SimProgram.run_buffered()   ~0,4–5,6 ms
                                             └─ publication du snapshot
                                                    │
  renderer (rAF 60 Hz) ◄── double/triple buffer ◄───┘
                            (SAB, seqlock)
```

Un seul `SharedArrayBuffer` porte les trois zones ; l'onglet doit être
**cross-origin isolated** (en-têtes COOP/COEP, cf. PLAN.md phase 2 tâche 7 —
`bench/server.mjs` les sert déjà).

### 7.2 Disposition du `SharedArrayBuffer`

| zone | contenu |
|---|---|
| en-tête (`Int32Array`, 16 mots) | `[seq, publishedIndex, tic, inputHead, inputTail, …]` |
| anneau d'entrées | N `ticcmd` de 1 felt, écrits par le thread principal, lus par le Worker |
| snapshots | **3** tampons de rendu de taille fixe (triple buffer) |

Le **snapshot de rendu n'est pas l'état complet** : le renderer n'a besoin que
de la position/angle du joueur, de la liste des mobjs visibles, de l'éclairage
des secteurs et du HUD — quelques kilo-octets, pas les 48 ko d'état. L'état
complet, lui, n'a aucune raison de sortir du Worker : il reste dans la mémoire
linéaire wasm entre deux tics, et seul le snapshot est publié.

### 7.3 Publication : seqlock sur triple buffer

Côté sim, après chaque tic :

```js
const next = (published + 1) % 3;          // jamais celui que lit le renderer
writeSnapshot(snapshots[next]);            // écriture pleine, sans verrou
Atomics.store(header, TIC, tic);
Atomics.store(header, PUBLISHED, next);    // publication atomique
Atomics.add(header, SEQ, 1);
```

Côté renderer, à chaque `requestAnimationFrame` :

```js
const s0 = Atomics.load(header, SEQ);
const i = Atomics.load(header, PUBLISHED);
const view = snapshots[i];                 // lecture directe, sans copie
render(view, snapshots[(i + 2) % 3], alpha);
if (Atomics.load(header, SEQ) !== s0) retry();   // le sim a publié pendant la lecture
```

Le **troisième** tampon existe pour l'interpolation demandée par PLAN.md
(phase 2, tâche 2) : le renderer a besoin des tics `N−1` et `N` simultanément,
et le sim doit pouvoir écrire `N+1` sans écraser `N−1`. Le renderer ne copie
rien : il lit des vues typées sur le `SharedArrayBuffer`. Le coût mesuré au
§4.4 (0,0025 ms pour 48 ko) montre que même une copie complète serait
indolore ; le triple buffer est là pour l'absence de déchirement et pour
l'interpolation, pas pour la performance.

### 7.4 Ordonnanceur 35 Hz et rattrapage

Pas de `setInterval` (dérive cumulée), pas de `requestAnimationFrame` (60 Hz,
gelé quand l'onglet est caché). Accumulateur à pas fixe sur `setTimeout` :

```js
const TIC_MS = 1000 / 35;                  // 28,571 ms
let next = performance.now();
function loop() {
  let ran = 0;
  while (performance.now() >= next && ran < MAX_CATCHUP) {
    stepTic(readTiccmd(tic));               // 0,4 ms (4 k steps) … 5,6 ms (52 k)
    tic += 1; next += TIC_MS; ran += 1;
  }
  if (performance.now() >= next) next = performance.now(); // abandon du retard
  setTimeout(loop, Math.max(0, next - performance.now()));
}
```

* `MAX_CATCHUP = 4` : on rattrape au plus 4 tics par réveil. Quatre tics à
  5,6 ms tiennent en 22 ms, sous le budget d'un tic, donc le rattrapage ne peut
  pas s'auto-entretenir (pas de *spiral of death*).
* Au-delà, on **abandonne le temps perdu** (`next = now`) : on ne fabrique
  jamais de tics d'entrée vides, car le journal de `ticcmd` doit rester
  exactement ce qui sera prouvé.
* **Onglet caché** : les timers sont bridés à ~1 Hz. Politique retenue :
  détecter `document.visibilityState === 'hidden'` et **mettre la partie en
  pause de façon déterministe** (PLAN.md phase 2 tâche 3), plutôt que de
  rattraper des dizaines de tics à la réapparition. Le compteur de tics ne
  saute pas : la preuve reste une suite contiguë de tics.
* **Entrées** : le thread principal écrit les `ticcmd` dans l'anneau
  (`Atomics.store` + `Atomics.notify`) ; le Worker consomme celui du tic `N`.
  Si le `ticcmd` du tic `N` n'est pas encore arrivé, on répète le précédent —
  et c'est cette décision, prise dans le Worker, qui est enregistrée dans le
  journal. L'horloge n'entre **jamais** dans la simulation.
* **Priorité** : le prouveur en tâche de fond (R6-A1) tourne dans d'autres
  Workers avec `hardwareConcurrency − 2` threads ; le Worker sim, qui n'utilise
  que 1,5 % d'un cœur à 4 k steps et 20 % à 52 k, n'a pas besoin de priorité
  particulière.
