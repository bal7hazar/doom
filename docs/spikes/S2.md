# S2 — WASM64 build of the Stwo Cairo prover and first measurements in Chrome

Risk actions covered: **R1-A3** (build WASM64, measure in Chrome), **R11-A1** (reproducible
container build, hashed artifact), **R11-A2** (differences with upstream as patches),
**R11-A3** (wasm64 execution test in headless Chrome). Deliverable code: `prover/wasm/`
(README there for the build recipe and the ABI).

## 1. Question

Can the current monorepo prover (`starkware-libs/proving` @ `cd7bc5f`) be compiled to
`wasm64-unknown-unknown` reproducibly and run `execute → prove → verify` of a Scarb executable
inside Chrome, and what are the time and memory costs per trace size — enough to decide whether
**a 2^20-step segment is provable in Chrome in < 120 s and < 12 GB** (R1-A3 exit criterion)?

**Short answer: yes.** The build works with three 10-line patches; a 2^20-step segment
(bootloader included, leaf parameters, 96-bit security) proves in **35.6 s** and peaks at
**3.05 GiB** of wasm memory in headless Google Chrome 152 on the M2 Max, single-threaded,
verified in-browser, three runs within 0.1 s. Measured directly, not extrapolated.

## 3. Method

1. **Build** (`prover/wasm/build.sh`): the monorepo crates are git dependencies pinned by full
   hash, redirected by `[patch]` to `vendor/proving` (clone at that commit + `patches/proving-*`
   applied with `git apply`); `xxhash-rust` to a vendored crates.io tarball (checksum from
   `Cargo.lock`) + patch. The wasm ABI is hand-written (clealabs style, no wasm-bindgen):
   `alloc/dealloc`, `(ptr,len)` arguments, a 40-byte result header, host imports
   `log/random/now`. `SHA256SUMS` records the artifact hash. The command is the monorepo's own
   wasm64 CI `cargo check` turned into a cdylib `build` (+ SIMD128, memory and stack link args).
2. **Execute path** = the recursion leaf as `leaf_prover::prove_leaf` runs it: the executable's
   `Bootloader` entry point becomes a `Task::Cairo1Program` of the leaf simple bootloader
   (`program_hash_function = blake`, `single_page = true`), `cairo_run_program` with layout
   `all_cairo_stwo`, proof mode, no trace padding, no VM relocation, then
   `stwo_cairo_adapter::adapt` → `ProverInput` (bincode across the JS boundary).
3. **Prove/verify** = `stwo_cairo_prover::prover::prove_cairo::<Blake2sM31MerkleChannel>` /
   `cairo_air::verifier::verify_cairo_ex`; proof returned as bincode of the extended `CairoProof`;
   `proof_to_felts` gives the cairo-serde felt stream (on-chain / `scarb verify` format) whose
   length is the "proof felts" column.
4. **Measurements**: for each k, 3 runs with a **fresh wasm instance** per run (Worker
   terminated between runs, so memory is released and every run pays V8 tier-up). Per stage:
   wall time around the export call in the Worker; `WebAssembly.Memory.buffer.byteLength`
   after the call (linear memory never shrinks → peak wasm heap);
   `performance.measureUserAgentSpecificMemory()` from the page (whole agent cluster, async so
   its per-stage attribution is loose — its peak is what matters). Inside the prover, tracing
   spans are timed with `host.now()` and forwarded to the harness.
5. **References**: the same code path natively (`hellproof-prover-native`, `getrusage` max RSS)
   with 1 thread (the fair comparison for a single-threaded wasm) and with all 12 cores; the same
   module in Node 24.
6. Proof-lock rule respected: k20 runs (native and Chrome) take `$SCRATCH/.proof-lock`.

- `lifting_size_policy` (`auto` vs `at_least_preprocessed`) changes nothing here: with
  `include_all_preprocessed_columns = true` and 16 forced `memory_id_to_big` components every

- S0's parameter set is 9 % faster and 9 % smaller at 2^20 (40 % faster at 2^14: `blake2s`

  format is what the recursion route needs, so its numbers are the ones to plan with — the
  difference is small anyway.
- S0 reported "≈ 290 k felts flat" for its proofs; this harness counts 688 k felts with the same

### 4.5 Node 24 (same module, `bench-node.mjs`, k14, first working build)

prove 75.0 s, verify 63 ms, wasm memory 1.97 GiB, verified. Node's V8 13.6 is ~2.3× slower than
Chrome 152's V8 on this module (older Liftoff/TurboFan for memory64); Node is a convenience
runner, not a target. Node 22 cannot load the module at all (`invalid table elements limits
flags`: Memory64 with 64-bit table limits landed in V8 13.3).

### 4.6 What dominates

With the leaf parameters the cost is **fixed**: `canonical_small` = 10.2 M preprocessed cells
(156 columns of 2^20) and `at_least_preprocessed` lifts *every* committed tree to 2^21 rows, so
a 2^14 trace costs as much as a 2^18 one (≈ 27–33 s in Chrome, ≈ 1.85 GiB) and the
trace-proportional part only appears above 2^18 (+0.3 GiB and +3 s per doubling to 2^20). The
proof is 755 k felts / 4.2 MB regardless of k for the same reason (`include_all_preprocessed_columns`
+ lifted trees: 8 537 sampled columns).

## 5. Verdict

**R1-A3 criterion "2^20 steps in Chrome in < 120 s and < 12 GB": met on this machine with a
large margin — 35.6 s and 3.05 GiB, single-threaded, verified in-browser, 3/3 runs.**
Confidence: high for the measurement itself (direct, stable, at the exact ceiling of
`canonical_small`); medium for other hardware — the criterion asks for three machines (16 GB
Apple Silicon, 16 GB x86 Windows, 32 GB) and only the 64 GB M2 Max was measured. Extrapolation:
the run is single-core and memory-bound at 3.1 GiB, so a 16 GB laptop with a ~2× slower core
should land around 60–80 s and the same 3.1 GiB (Chrome's Memory64 cap is 16 GiB on all of
them); x86 SIMD128 lowering is comparable to arm64's. Remaining risk on 16 GB machines is
sharing RAM with the game tab and other processes, not the prover itself.

Consequences for the plan:
- The browser prover is viable **without threads** for the MVP; threads (wasm-bindgen-rayon or a
  hand-rolled pool over `SharedArrayBuffer`) are an optimisation (≤ 35 s → ~10 s), not a blocker.
- The fixed cost (~27 s, 1.85 GiB) means segments should be sized close to the 2^20 ceiling
  (R1-A4's 2^19 "useful" target costs the same time as 2^20 — there is no time reason to go
  smaller; the reason to keep margin is only the hard ceiling).
- The 43 MB module loads/compiles in < 0.1 s (streaming, lazy tier-up); size only matters for
  transfer (8.1 MB gzipped) — a `wasm-opt` pass and dropping the Cairo compiler crates (parse the
  executable in JS, pass bytecode + hints) are cheap follow-ups.

## 6. Blockers found, patches, follow-ups

### Blockers and how they were resolved

| # | Symptom | Cause | Resolution |
|---|---|---|---|
| 1 | `xxhash-rust 0.8.18` fails to compile on wasm64 with `+simd128` (`core::arch::wasm32` not found) | its SIMD path is gated on `target_family = "wasm"` but imports `core::arch::wasm32` | `patches/xxhash-rust-0.8.18-wasm64-simd128.patch` (gate on `target_arch = "wasm32"`) — PR to open upstream |
| 2 | `getrandom 0.2` on wasm64: `js` feature only covers wasm32 → compile error without `custom`; and *with* the monorepo's `js` feature, the module imports wasm-bindgen glue (`__wbg_getRandomValues_*`…) that Node/Chrome cannot satisfy | the prover crate enables `getrandom/js` + `wasm_js` for all wasm targets; in 0.2.17 `js` also covers wasm64 and wins over `custom` | crate enables `getrandom/custom` and defines `__getrandom_v03_custom` + `register_custom_getrandom!`; `patches/proving-0002` restricts the monorepo override to wasm32 — PR to open upstream |
| 3 | **Standalone executable route is broken upstream**: `Constraints not satisfied` (k14) or `TryFromIntError` in `extract_public_segments` (k16), also with the monorepo's own `run_and_prove --program_type executable` | `adapt()` hardcodes `PublicSegmentContext::bootloader_context()` (S0 found the same) | run under the leaf simple bootloader (`Task::Cairo1Program`), as the recursion does |
| 4 | leaf bootloader hint `DUMP_PRIVACY_SIMPLE_BOOTLOADER_OUTPUT_PREIMAGE` needs `std::fs::write` | wasm has no filesystem | `patches/proving-0001`: keep the preimage in the execution scopes, dump to file only if a path is given (returned as `output_preimage`) — PR to open upstream |
| 5 | `prove` panics on wasm: `ThreadPoolBuildError { Unsupported }` in `partial_ec_mul_window_bits_9` | three witness generators build their own 8 MiB-stack rayon pool and `unwrap()` (rayon's single-thread fallback only covers the global pool) | `patches/proving-0003`: run inline when the pool cannot be built — PR to open upstream |
| 6 | remaining `__wbindgen_placeholder__` imports (`__wbindgen_throw`, externref table helpers, JSPI spawn) | `web-time` ← `microlp` ← `good_lp` ← `cairo-lang-eq-solver` (Cairo compiler, never executed) | stubbed by the JS loader (throws if ever called); not a patch |
| 7 | Node 22 rejects the module (`invalid table elements limits flags`) | V8 < 13.3 lacks 64-bit table limits | use Node ≥ 24 (Chrome 152 is fine) |

Patches: **3 on the monorepo (+ 1 on xxhash-rust), ≤ 5 as R11-A2 requires**, each ≤ 12 lines,
listed with justification in `prover/wasm/patches/README.md`; none changes native behaviour.
Upstream PRs are still to be opened (follow-up).

### Follow-ups

1. **CI** (R11-A1/A3, orchestrator): a workflow that runs `prover/wasm/build.sh` in the
   `Dockerfile` on Linux and compares `SHA256SUMS` with a macOS build (two independent builds →
   same hash: `--remap-path-prefix` is set, the remaining suspects are `build-std` host paths);
   then `npm run test` (`bench.mjs --k 14 --runs 1 --ci` on Playwright Chromium, ~40 s).
2. **Threads**: wasm-bindgen ≥ 0.2.10x has wasm64 support (usize lowered as f64) but
   `--target web` + `wasm-bindgen-rayon` on memory64 were not tried; alternatively a hand-rolled
   pool (shared `WebAssembly.Memory`, `+atomics`, `-Z build-std` with atomics, one Worker per
   thread) behind the same ABI. Expected gain: grind 4.8 s and commitments ~8 s are embarrassingly
   parallel; Prove STARKs partly. Target ≈ 10–15 s at 2^20 on 8 cores.
3. **Module size** (43 MB): `wasm-opt -O2 --enable-memory64`, and/or parse the executable in JS
   and drop `cairo-lang-executable/runner`'s compiler dependencies (they bring `salsa`,
   `microlp`, `xxhash`…), which also removes blockers 1 and 6.
4. **Other machines** (R1-A3 asks for three): run `npm run bench` on a 16 GB Apple Silicon and a
   16 GB x86 Windows machine; `--channel chromium` for the Playwright build.
5. **Parameters**: S4 must confirm the leaf parameter set (`include_all_preprocessed_columns`,
   lifting) against the `doom` registry; `fold_step = 4` (S0: −0.29 GiB, −12 % proof) is worth
   measuring in wasm once the registry fixes `fold_step`.
6. **Segment sizing** (R1-A4): dimension K from the *total* step count (bootloader ≈ 2 340 +
   14.7 × bytecode words, S0) against the 2^20 ceiling; the harness' `execute` returns `n_steps`.
7. Upstream PRs for the three monorepo patches and the xxhash-rust one.
