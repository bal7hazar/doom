# S0 — Pipeline de preuve de référence

> Spike PRV, lane S0 du [ROADMAP](../../ROADMAP.md) §1. Actions couvertes :
> **R1-A1**, **R1-A2**, **R1-A5**, **R4-A1**. Mesures du **2026-09-12** sur
> M2 Max 12 cœurs / 64 GB. Répertoire de travail : [`spikes/s0/`](../../spikes/s0).

---

## 1. Question

Peut-on prouver **un exécutable Scarb `#[executable]`** avec le prouveur du monorepo
`starkware-libs/proving` épinglé, en utilisant la trace pré-traitée **`canonical_small`**,
et un segment « taille navigateur » de **≤ 2^20 steps** tient-il dans un budget mémoire
compatible avec WASM64 (< 16 GB, cible < 12 GB) ?

Sous-questions :

1. Quelle est la **séquence de commandes exacte** (route la plus courte qui marche) ?
2. Quels **paramètres de prouveur** prendre comme référence, et lesquels la route
   récursive impose-t-elle ?
3. Les deux **paniques** observées avec le prouveur embarqué de Scarb 2.16 (felt ≥ 2^128
   en mémoire, builtin bitwise) se reproduisent-elles ? (**R4-A1**)
4. Quelle est la **courbe RSS = f(log steps)** et quels **leviers** la font bouger ?
   (**R1-A2**, **R1-A5**)
5. Combien coûte le **bootloader** en steps ?

## 3. Méthode

### 3.1 La séquence de commandes qui marche

**Route retenue : « exécutable Scarb comme tâche du privacy simple bootloader ».**
C'est aussi la route qu'exige la chaîne récursive (S4).

```bash
# 1. compiler l'exécutable Scarb (enable-gas = false, [[target.executable]])
cd spikes/s0/programs/steps_k
ASDF_SCARB_VERSION=2.19.4 scarb build
#    -> target/dev/steps_k.executable.json

# 2. arguments : tableau JSON de felts en hexadécimal (format BigUintAsHex),
#    identique à `scarb execute --arguments-file`
echo '["0x14"]' > args.json          # k = 20

# 3. décrire la tâche pour le bootloader (chemins ABSOLUS obligatoires)
cat > bl_input.json <<EOF
{
  "tasks": [
    {
      "type": "Cairo1Executable",
      "path": "/abs/path/steps_k.executable.json",
      "program_hash_function": "blake",
      "user_args_file": "/abs/path/args.json"
    }
  ],
  "fact_topologies_path": null,
  "single_page": true,
  "output_preimage_dump_path": "/abs/path/out/output_preimage.json"
}
EOF

# 4. (optionnel mais recommandé) mesurer la trace sans prouver
stwo-vm-runner \
  --program  $PROVING/crates/cairo-program-runner-lib/resources/compiled_programs/bootloaders/privacy_simple_bootloader_compiled.json \
  --program_input bl_input.json \
  --layout all_cairo_stwo \
  --output_execution_resources_path    out/execution_resources.json \
  --output_vm_execution_resources_path out/vm_execution_resources.json

# 5. exécuter + prouver + vérifier, en une commande
stwo-run-and-prove \
  --program  .../privacy_simple_bootloader_compiled.json \
  --program_input bl_input.json \
  --prover_params_json spikes/s0/params/canonical_small.json \
  --proof_path   out/proof.cairo_serde.json \
  --proof-format cairo-serde \
  --program_output out/program_output.json \
  --verify

# 6. vérification autonome (le binaire `verify` ne lit que le format json)
verify --proof_path out/proof.json --channel_hash blake2s
```

Tout cela est encapsulé dans [`spikes/s0/scripts/prove.sh`](../../spikes/s0/scripts/prove.sh)
(`prove.sh <executable.json> <args.json> <out_dir>`), qui pose en plus le verrou de preuve
partagé au-delà de 2^19 steps.

**Pièges de la ligne de commande**

* Le flag est `--proof-format` (tiret) alors que tous les autres sont en `snake_case`
  (`--proof_path`, `--program_input`, `--prover_params_json`). Les valeurs sont
  `json`, `cairo-serde` (tiret aussi), `binary`, `extended-binary`.
* `--program` de `stwo-run-and-prove` attend un **programme Cairo 0 compilé**. Lui passer
  un `.executable.json` de Scarb échoue avec `missing field instruction_locations` : c'est
  le bootloader qui est le `--program`, l'exécutable Scarb est une *tâche* dans
  `--program_input`.
* Les chemins dans `bl_input.json` doivent être **absolus** (ils sont résolus à la
  désérialisation, pas relativement au fichier).
* `output_preimage_dump_path` est **obligatoire** pour le *privacy* simple bootloader
  (`PrivacySimpleBootloaderInput`), et le répertoire doit exister.
* `program_hash_function` accepte `pedersen`, `poseidon`, `blake` (insensible à la casse).
  Le choix a un coût **très** différent, voir §5.5.
* `--layout` : `all_cairo_stwo` (ce que `stwo-run-and-prove` force en interne). Scarb
  utilise `stwo_no_ecop` par défaut ; les comptes de steps sont identiques.

### 3.2 Route « standalone » (sans bootloader) — **cassée**

`stwo-cairo-dev-utils` expose `run_and_prove --program_type executable
--program_arguments_file args.json`, qui exécute l'entrypoint `Standalone` de
l'exécutable sans bootloader. C'est la route la plus courte **sur le papier** ;
en pratique elle échoue sur **tous** nos programmes, voir §5.4. Ne pas l'utiliser.

### 3.3 Fichiers produits

| Fichier | Contenu |
|---|---|
| `execution_resources.json` | ressources *post-adaptateur* (arrondies aux puissances de 2 par builtin) |
| `vm_execution_resources.json` | `n_steps`, `n_memory_holes`, comptes de builtins **bruts** de la VM |
| `program_output.json` | sortie du bootloader : 2 felts (le hash blake2s packé de la sortie) |
| `output_preimage.json` | préimage : `[n_tasks, output_size, program_hash, task_output…]` |
| `proof.cairo_serde.json` | tableau JSON de felts hexadécimaux — le format à sérialiser on-chain |

Exemple pour `felt_loop(1000)` :

```json
program_output   ["0x82042efd484736f663f1d7ff1cc2cd2c", "0x3a1db71f395c0379314812de0228d4da"]
output_preimage  ["0x1", "0x3", "0x5505b4a5…2977", "0x25a732fe…5e0"]
                   ^n_tasks ^size ^program_hash(blake) ^sortie de la tâche
```

C'est exactement la structure sur laquelle S4 devra rebrancher la chaîne `h_in/h_out`.

### 3.4 Programmes de test

Sept paquets Scarb autonomes dans [`spikes/s0/programs/`](../../spikes/s0/programs),
tous avec `[[target.executable]]` et `enable-gas = false` :

| paquet | ce qu'il exerce | argument(s) |
|---|---|---|
| `felt_loop` | arithmétique felt252 pure **avec valeurs négatives** (`5 - acc`, donc des felts ≥ 2^128) écrites en mémoire via un `Array` | `n` |
| `u32_loop` | `wrapping_add`/`mul`/`sub` sur u32 → builtin range_check | `n` |
| `bitwise_loop` | `&` et `^` sur u64 → **builtin bitwise** | `n` |
| `poseidon_hash` | `poseidon_hash_span` sur un tableau de `n` felts → builtin poseidon | `n` |
| `steps_k` | boucle felt252 calibrée pour que `n_steps ≈ 2^k` | `k` |
| `bigcode` | 16 114 mots de bytecode, run court : isole le terme « taille du programme » du surcoût bootloader. Source générée par `generate.py` | `n` |
| `felt_width` | même flux d'opcodes, valeurs mémoire au-dessus/au-dessous du seuil 2^72 de l'adaptateur | `n`, `shift` |

Calibration de `steps_k` : le modèle mesuré est
`n_steps(k) = (65 + 14·k) + 6 · iters`, avec `iters = (2^k − 400)/6`, ce qui place le
compte réel 55 à 111 steps **sous** 2^k pour k ∈ [16, 21] :

| k | 16 | 17 | 18 | 19 | 20 | 21 |
|---|---:|---:|---:|---:|---:|---:|
| `n_steps` (sans bootloader) | 65 425 | 130 971 | 262 061 | 524 215 | 1 048 521 | 2 097 107 |
| écart à 2^k | −111 | −101 | −83 | −73 | −55 | −45 |

## 4. Paramètres de référence (R1-A1)

Fichiers dans [`spikes/s0/params/`](../../spikes/s0/params), documentés dans
[`params/README.md`](../../spikes/s0/params/README.md).

`canonical_small.json` — **la référence pour un segment Hellproof** :

```json
{ "channel_hash": "blake2s", "channel_salt": 0,
  "fri_config": { "pow_bits": 26, "log_blowup_factor": 1,
                  "log_last_layer_degree_bound": 0, "n_queries": 70, "fold_step": 1 },
  "preprocessed_trace": "canonical_small",
  "store_polynomials_coefficients": false,
  "include_all_preprocessed_columns": false,
  "opt_n_id_to_big_components": null,
  "lifting_size_policy": "auto" }
```

* Les **deux** canaux Blake2s existent et fonctionnent sur ce commit :
  `blake2s` et `blake2s_m31` (`canonical_small_m31.json`). Preuve produite et
  **vérifiée** avec chacun ; vérifier une preuve `blake2s_m31` en `blake2s` échoue
  proprement (`Proof of work verification failed`). La route récursive utilise
  `Blake2sM31` côté *privacy* (`crates/privacy_prove/src/consts.rs`) mais `blake2s`
  côté *recursive_tree* (`test_data/cairo_prover_params.json`) : **ce n'est pas un
  choix unique**, S4 tranchera.
* `preprocessed_trace = canonical_small` plafonne la trace à **2^20**
  (`max_log_trace_size()`), bootloader compris. C'est la contrainte structurante.
* `include_all_preprocessed_columns = false` : gain net sur la taille de preuve, sans
  effet mesurable sur la RSS (§6).

Ce que la route récursive impose vraiment (à ne pas confondre avec notre référence) :
`circuit_registry_definitions/canonical_small/definition.json` pointe sur
`crates/stwo_run_and_prove_recursive_tree/test_data/cairo_prover_params.json`, copié tel
quel dans `params/recursion_tree_reference.json` : **`pow_bits = 16`**,
`include_all_preprocessed_columns = true`, `lifting_size_policy = at_least_preprocessed`,
`opt_n_id_to_big_components = 16`. Le registre fixe aussi `min = max = 20` pour
`trace_log_size` — donc **toutes** les feuilles doivent faire exactement 2^20.

## 5. Résultats

> Toutes les tables sont regénérées par `python3 spikes/s0/scripts/tables.py` depuis
> `spikes/s0/results/*/summary.json`.
>
> **Fiabilité des chiffres.** RSS, tailles de preuve et comptes de steps/composants sont
> déterministes et reproductibles. Les **temps** le sont beaucoup moins ici, pour deux
> raisons cumulées : (a) la machine est partagée avec S2/S4 (load moyen observé 13–17),
> et sous sur-souscription rayon brûle du temps *user* en attente, ce qui gonfle la
> colonne CPU ; (b) le **grind de proof-of-work** à `pow_bits = 26` est une variable
> géométrique amorcée par la trace : reproductible pour une trace donnée, mais arbitraire
> d'une trace à l'autre, elle ajoute 1 à 3 s de CPU. C'est pourquoi la courbe d'échelle
> de référence est mesurée à `pow_bits = 0` (`canonical_small_pow0.json`, mesure
> uniquement : sécurité 70 bits au lieu de 96).

### 5.1 Les cinq programmes de référence passent la chaîne complète

Exécution → prover input → preuve → vérification, route bootloader, `canonical_small` :
**5/5 OK**, y compris `felt_loop` (felts ≥ 2^128 en mémoire) et `bitwise_loop`
(builtin bitwise). `felt_width` passe aussi (§5.5) ; `bigcode` n'a servi qu'à la
mesure VM de §5.2.

Coûts par itération mesurés au passage (`scarb execute --print-resource-usage`, n = 1000) :
`felt_loop` **36,0 steps/it** (arithmétique felt252 + écriture mémoire + relecture),
`u32_loop` **43,0 steps/it** et 6 range_check/it, `bitwise_loop` **16,1 steps/it** et
2 bitwise/it, `poseidon_hash` **23,6 steps/felt haché** et 0,5 poseidon/felt.
Note : le builtin **bitwise apparaît (1 instance) dans *toutes* les traces sous
bootloader** — le bootloader lui-même l'utilise. Le lint « pas de bitwise » de R1-A1
doit donc porter sur le *programme applicatif*, pas sur la trace complète.

### 5.2 Coût du bootloader : constant + **proportionnel à la taille du programme**

`spikes/s0/results/bootloader-overhead.tsv`. Le bootloader charge la tâche en mémoire
**et la hache** ; le terme dominant est donc proportionnel au nombre de mots de bytecode,
pas au temps d'exécution. `bigcode` (16 114 mots, run de 8 034 steps) le rend visible :

| programme | mots de bytecode | hash | steps seuls | + bootloader | surcoût |
|---|---:|---|---:|---:|---:|
| `bitwise_loop` | 210 | blake | 68 | 5 498 | 5 430 |
| `u32_loop` | 277 | blake | 59 | 6 499 | 6 440 |
| `felt_loop` | 312 | blake | 85 | 7 063 | 6 978 |
| `felt_width` | 323 | blake | 34 054 | 41 166 | 7 112 |
| **`bigcode`** | **16 114** | blake | 8 034 | 247 920 | **239 886** |
| `bitwise_loop` | 210 | poseidon | 68 | 3 066 | 2 998 |
| `felt_loop` | 312 | poseidon | 85 | 3 634 | 3 549 |
| **`bigcode`** | **16 114** | poseidon | 8 034 | 98 501 | **90 467** |

Modèles ajustés (2 points extrêmes, erreur < 2 % sur les points intermédiaires) :

```
program_hash_function = "blake"     surcoût ≈  2 340 + 14,74 × mots   (+1 range_check/mot)
program_hash_function = "poseidon"  surcoût ≈  1 840 +  5,50 × mots   (+0,5 poseidon/mot)
```

**Conséquence pour R1-A4.** L'hypothèse « bootloader ≈ 30 k steps » du RISKS est fausse
dans les deux sens : c'est ~6,5 k pour un programme jouet, mais **240 k steps pour un
programme de 16 k mots** en blake — soit 23 % d'un budget de 2^20. Un cœur Doom sera
nettement plus gros que 16 k mots. Deux leviers immédiats :

1. passer le hash de tâche à **poseidon** : ÷2,7 sur le terme proportionnel (à valider
   côté route récursive en S4 — la préimage de sortie contient ce hash) ;
2. mesurer `bytecode_words` du cœur Doom **dès S1** et l'intégrer au calcul de K
   (tics/segment) : le budget utile est `2^20 − (2 340 + 14,74 × mots)`, pas `2^20`.

Trois lectures :

* **La part fixe de `canonical_small` est ~2,2 GiB** (extrapolation à 0 step des points
  k = 18 → 21 : 2,17 GiB), contre **~15,9 GiB pour `canonical`**. Ratio 7,3× sur la RSS
  (le ratio 53× sur le nombre de cellules pré-traitées ne se transporte pas tel quel :
  l'arbre de Merkle et le blow-up dominent). Le critère de sortie de **R1-A2
  (« part fixe < 3 GB ») est tenu**.
* La pente est de **~1,8 GiB par million de steps** au-delà de 2^18.
  `RSS(k) ≈ 2,2 GiB + 1,8 GiB × steps/10^6`.
* Le surcoût de `canonical` est **entièrement** dans un seul span :
  `Compute preprocessed trace commitment` = **3,3–3,5 s** contre 0,09 s pour
  `canonical_small` (table E). C'est bien la trace pré-traitée, et rien d'autre, qui
  paie — ce que R1-A2 demandait de séparer.

**Le plafond 2^20 de `canonical_small` n'est pas ce qu'on croyait.** k = 20 (1 055 051
steps) *et* k = 21 (2 103 637 steps) passent et se vérifient. En lisant
`crates/prover/src/prover.rs:137`, `max_log_trace_size()` ne sert qu'à dimensionner le
*lifting de l'arbre pré-traité* ; aucune assertion ne borne la trace principale. Avec
`lifting_size_policy = auto` les deux arbres sont liftés indépendamment, donc une trace
> 2^20 passe. La borne réapparaît dès qu'on fixe le lifting : `fixed(20)` à k = 19 échoue
proprement avec `Lifting log size is too small (20). It must be at least 21.`
**Le plafond de 2^20 est donc une contrainte de la route récursive** (registre
`min = max = 20`, lifting fixé), pas du prouveur ; il reste la contrainte de conception,
mais il ne bloque pas les mesures ni un éventuel repli non récursif.

### 5.4 La route « standalone » est cassée sur ce commit

| programme | args | steps | résultat |
|---|---|---:|---|
| `felt_loop` | 0x0 | 59 | **FAIL** — `Constraints not satisfied.` |
| `felt_loop` | 0x1 | 85 | **FAIL** — `Cannot convert F252 to u128` (`adapter/src/memory.rs:286`) |
| `felt_loop` | 0x3e8 | 36 049 | **FAIL** — idem |
| `poseidon_hash` | 0x3e8 | 23 565 | **FAIL** — idem |
| `u32_loop` | 0x3e8 | 43 016 | **FAIL** — `Result::unwrap()` on `Err(TryFromIntError)` |
| `bitwise_loop` | 0x3e8 | 16 052 | **FAIL** — idem |

Cause racine (lue dans le code) : `crates/prover/src/witness/cairo.rs:28`,
`extract_public_segments`, lit les pointeurs de début/fin des segments de builtins aux
adresses `initial_ap … initial_ap+n` et `final_ap−n … final_ap` :

```rust
let value = memory.get(addr).as_small().try_into().unwrap();
```

Sous l'entrypoint `Standalone` d'un exécutable Scarb, ces cellules contiennent les
**valeurs de retour du programme**, pas des pointeurs de segment. Le symptôme dépend donc
de ce que le programme retourne : `TryFromIntError` si c'est un petit felt qui ne tient
pas dans un `u32`, l'assertion `Cannot convert F252 to u128` si c'est un felt ≥ 2^128,
et `Constraints not satisfied` quand la valeur passe les deux filtres par chance.
Le `ProverInput` construit par
`crates/dev_utils/src/vm_utils.rs::get_program_and_hints_from_executable` est malformé
pour un exécutable Scarb. **Reproducteur minimal : n'importe quel exécutable Scarb**,
p. ex. `felt_loop` avec `n = 0` (59 steps).

### 5.5 R4-A1 — verdict sur les deux paniques

| Panique (Scarb 2.16) | Route bootloader (la nôtre) | Route standalone |
|---|---|---|
| `Cannot convert F252 to u128`, felt ≥ 2^128 en mémoire (`memory.rs:291`) | **Ne se reproduit pas.** `felt_loop(1000)` écrit 1 000 felts ≥ 2^128 en mémoire (et en retourne un) : preuve produite **et vérifiée**. `felt_width` avec des valeurs ~2^132 : idem. | Se reproduit (`memory.rs:286`), mais comme **symptôme du bug de route** de §5.4, pas comme limite de l'adaptateur. |
| `index out of bounds` (`memory.rs:96`) avec le builtin **bitwise** | **Ne se reproduit pas.** `bitwise_loop(1000)` = 2 002 instances bitwise : preuve produite **et vérifiée**. | Ne se reproduit pas non plus (autre panique en amont). |

**Conclusion R4-A1 : les deux interdits provisoires de CONTEXT §4.3 peuvent être levés.**
Le prouveur du monorepo à `cd7bc5f` accepte les felts ≥ 2^128 en mémoire et le builtin
bitwise. Ce qui reste vrai :

* Une exécution qui **panique** reste improuvable — R4-A2/A3/A4 restent entiers.
* Il subsiste un **seuil de coût**, pas de correction, à **2^72** (et non 2^128) :
  `MemoryConfig::default().small_max = (1 << 72) − 1` et
  `adapter/src/memory.rs::value_from_felt252` classent une cellule mémoire en
  `Small(u128)` seulement si le felt est < 2^72 ; au-delà elle part sur le chemin `F252`.
  Mesuré avec `felt_width` (flux d'opcodes **identique** à ±3 opcodes sur 41 000, seules
  les valeurs stockées changent) :

  | | `narrow` (valeurs ~2^52) | `wide` (valeurs ~2^132) |
  |---|---:|---:|
  | steps | 41 166 | 41 172 |
  | `range_check_9_9_{,B,C,D}` | 24 576 | **32 768** |
  | `range_check_9_9_{E,F}` / `{G,H}` | 8 192 / 4 096 | **16 384 / 8 192** |
  | `range_check_20_*`, `memory_id_to_big`, `opcodes`, tout le reste | identiques | identiques |
  | RSS max | 2,29 GiB | 2,32 GiB |
  | CPU (pow 26, 4 exécutions) | 35,6–36,1 s | 20,6–21,6 s |
  | CPU (pow 0) | 22,0 s | 16,1 s |

  Donc : **la trace des grands felts est strictement plus grande** (+33 % sur les huit
  composants `range_check_9_9_*`, rien d'autre ne bouge) et la RSS est inchangée. En
  revanche le *temps* va systématiquement dans l'autre sens — écart reproductible sur
  quatre exécutions, y compris à `pow_bits = 0` — et **S0 n'explique pas pourquoi**.
  Tant que ce n'est pas élucidé (suite **F3**), on ne peut pas chiffrer un coût temps des
  grands felts, dans un sens ni dans l'autre.

  La règle de conception « felt-first, valeurs mémoire < 2^72 » (l'encodage à offset 2^40
  de R2-A4 y est très largement) reste raisonnable au vu de la taille de trace, mais elle
  n'est **plus une condition de prouvabilité** — seulement une préférence, et même son
  bénéfice en temps est à confirmer.

### 5.6 Taille de preuve : constante

**~4,33 MB / ~290 000 felts** quel que soit k de 2^16 à 2^21 et quelle que soit la trace
pré-traitée. La taille est fixée par `n_queries = 70` et le nombre de composants, pas par
la taille de la trace. Deux variations :

* `include_all_preprocessed_columns = true` (imposé par la route récursive) :
  **+0,8 %** (4,37 MB) sur nos params, mais **+23 %** (5,15 MB / 357 000 felts) avec le
  fichier `recursion_tree_reference.json` complet.
* `fold_step = 4` : **−12 %** (3,83 MB / 257 681 felts).

Pour mémoire, la preuve **racine** de la route récursive fait ≈ 36 000 felts : les 290 k
felts d'une preuve Cairo de segment ne vont jamais on-chain, ils vont au `leaf_prover`.
Le format `json` du même objet pèse 11,4 MB, soit 2,6× le `cairo-serde` : n'utiliser
`json` que pour le vérifieur Rust autonome.

## 6. Leviers mémoire (R1-A5)

Un seul bouton changé à la fois par rapport à `canonical_small`, sur `steps_k(19)`
(530 745 steps, bootloader compris) :

| variante | RSS max (GiB) | Δ RSS | preuve (MB) | preuve (felts) | résultat |
|---|---:|---:|---:|---:|---|
| `baseline` (= `canonical_small`) | 3,337 | — | 4,33 | 289 295 | OK |
| `store_polynomials_coefficients = true` | 3,699 | **+0,362** | 4,33 | 289 295 | OK |
| `include_all_preprocessed_columns = true` | 3,429 | +0,092 | 4,37 | 291 303 | OK |
| `lifting_size_policy = at_least_preprocessed` | 3,304 | −0,033 | 4,33 | 289 295 | OK |
| `fold_step = 2` | 3,186 | −0,151 | 3,91 | 262 603 | OK |
| `fold_step = 4` | 3,050 | **−0,287** | 3,83 | 257 681 | OK |
| `lifting_size_policy = fixed(20)` | 1,120 | — | — | — | **FAIL** — `Lifting log size is too small (20). It must be at least 21.` |

Lecture :

* **`store_polynomials_coefficients = false` est le bon choix** et l'est déjà par défaut :
  le mettre à `true` coûte **+0,36 GiB** (+11 %) pour rien ici. C'est le seul levier qui
  déplace la mémoire de façon franche parmi ceux qui ne changent pas la preuve.
* **`fold_step` est un gain gratuit sur les trois axes** : `4` donne −0,29 GiB de RSS
  **et** −12 % de taille de preuve. À ne pas activer à l'aveugle : `fold_step` fait partie
  du `FriConfig` que le vérifieur reconstruit, donc le vérifieur Cairo/circuit doit
  l'accepter. À valider en S4 avant de l'inscrire dans les params de référence.
* `include_all_preprocessed_columns` coûte peu en RSS (+0,09 GiB) ; son vrai coût est la
  taille de preuve. La route récursive l'impose, on n'a pas le choix là-bas.
* `lifting_size_policy` n'a **pas** d'effet mémoire (−0,03 GiB, dans le bruit) : c'est un
  paramètre de **compatibilité vérifieur**, pas un levier mémoire.
* `fixed(20)` échoue à k = 19 : à `log_blowup_factor = 1`, un lifting fixé à 20 impose
  une trace ≤ 2^19. C'est le mécanisme réel derrière le « plafond 2^20 » (§5.3).

**Ce qui domine la mémoire.** Par ordre décroissant, d'après les spans (table E) et la
courbe RSS :

1. **la trace pré-traitée et sa commitment** — part fixe : 15,9 GiB en `canonical`,
   2,2 GiB en `canonical_small`. C'est *le* facteur, à un ordre de grandeur des autres ;
   le span `Compute preprocessed trace commitment` passe de 3,4 s à 0,09 s entre les deux.
2. **la trace principale + son extension FRI** — ~1,8 GiB par million de steps ;
   dans les spans, `Write Base trace` + `Compute base trace commitment` croissent
   linéairement (0,13 s à k = 16 → 2,3 s à k = 21).
3. **les coefficients de polynômes conservés** — +0,36 GiB, désactivés par défaut.
4. le reste (trace d'interaction, composition, FRI) est sous le bruit de mesure.

Aucun allocateur transitoire ne domine : il n'y a donc rien à proposer en amont côté
« mode low-memory » (dernier volet de R1-A5) — le seul vrai levier était le choix de la
trace pré-traitée, et il est déjà exposé.

## 7. Verdict

> **GO** — « des segments de taille navigateur (≤ 2^20 steps) sont prouvables avec
> `canonical_small` » est **vérifié**, avec une marge confortable.

Ce qui est établi :

| Critère | Attendu | Mesuré | Verdict |
|---|---|---|---|
| Pipeline exécutable Scarb → preuve → vérif | doit exister | route bootloader, une commande, 5/5 programmes | **OK** |
| RSS d'un segment 2^20 (`canonical_small`) | < 12 GB (R1-A3), < 16 GB (Memory64) | **4,05 GiB natif** | **OK, ×3 de marge** |
| Part fixe de la mémoire | < 3 GB (R1-A2) | **2,2 GiB** | **OK** |
| Temps d'un segment 2^20 | 30–120 s en WASM | **5,0 s natif 12 cœurs** → 25–100 s à 5–20× | **plausible** |
| `canonical_small` + Blake2sM31 | doit exister pour la récursion | les deux canaux marchent et se vérifient | **OK** |
| Paniques R4 (felt ≥ 2^128, bitwise) | à confirmer | **aucune des deux ne se reproduit** | **levées** |

Les réserves, par ordre d'importance :

1. **Le bootloader coûte cher pour un gros programme** (§5.2) : `2 340 + 14,7 × mots de
   bytecode` steps en blake. C'est le risque n° 1 sur le dimensionnement de K et il
   n'était pas au budget. Il faut la taille du bytecode du cœur Doom (S1) pour conclure.
   → **GO avec cette réserve**, à re-trancher à G0 avec le chiffre de S1.
2. **Le plafond 2^20 vient de la route récursive, pas du prouveur** (§5.3) : c'est le
   registre de circuits (`min = max = 20`) et le lifting fixé qui l'imposent. S4 doit le
   confirmer sur son propre registre ; si le registre `doom` autorisait 2^21, la marge
   doublerait. La contrainte de conception reste 2^20 tant que S4 n'a pas tranché.
3. **La marge navigateur est estimée, pas mesurée.** 4,2 GiB natif ne garantit pas
   < 12 GB en WASM64 : allocateur différent, pas de SIMD portable garanti, pas de
   `madvise`. C'est exactement l'objet de S2, qui peut maintenant partir avec des params
   figés.
4. **Les temps de cette note sont des majorants bruités** (machine partagée + grind PoW).
   Ils suffisent pour un ordre de grandeur, pas pour un budget.

Ce que S0 verrouille pour les autres lignes :

* **Params de référence** : `spikes/s0/params/canonical_small.json` (R1-A1 fait).
* **Commande de référence** : §3.1, encapsulée dans `spikes/s0/scripts/prove.sh`.
* **Règle A7 assouplie** (R4-A1) : felts ≥ 2^128 et bitwise autorisés ; garder
  « valeurs mémoire < 2^72 » comme optimisation, pas comme contrainte de prouvabilité.
* **Budget de segment** : `steps_utiles ≤ 2^20 − (2 340 + 14,7 × mots_de_bytecode)`,
  à instancier avec la mesure S1.

## 9. Reproduire

```bash
# 1. cloner et construire le prouveur épinglé (ne PAS construire dans un clone partagé)
git clone https://github.com/starkware-libs/proving ~/git/proving
cd ~/git/proving && git checkout cd7bc5f4697fb188a27e09f9242f1dd76df8afdc
RUSTFLAGS="-C target-cpu=native -C opt-level=3" cargo build --release \
  -p stwo-cairo-dev-utils -p stwo-run-and-prove -p stwo-vm-runner     # ~6 min

# 2. installer Scarb 2.19.4
asdf install scarb 2.19.4

# 3. construire les programmes de test et rejouer la matrice
cd <repo>/spikes/s0
export PROVING_DIR=~/git/proving          # défaut de scripts/env.sh
./scripts/build.sh
./scripts/resources.sh                    # scarb --print-resource-usage
./scripts/bootloader_overhead.sh          # coût du bootloader = f(taille du programme)
./scripts/measure.sh                      # matrice complète -> results/

# une seule preuve, à la main
./scripts/prove.sh programs/steps_k/target/dev/steps_k.executable.json \
                   args/k19.json /tmp/out
./scripts/verify.sh /tmp/out/proof.json blake2s     # nécessite PROOF_FORMAT=json
```

Toutes les sorties brutes (`/usr/bin/time -l`, `scarb --print-resource-usage`,
`summary.json` par exécution) sont dans [`spikes/s0/results/`](../../spikes/s0/results).
Les preuves elles-mêmes ne sont pas versionnées (4–12 MB pièce) ; leurs tailles sont dans
les tables ci-dessus.
