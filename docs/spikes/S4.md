# S4 — Route récursive à N feuilles sur le monorepo `proving` (R3-A2, A3, A4, A8)

## Question

**N preuves de segments (≤ 2^20 steps chacune) se replient-elles en une seule preuve racine acceptée
par le vérifieur de circuit on-chain (`stwo_circuit_verifier`), avec des sorties de feuilles
recomposables on-chain ?** Sous-questions : quel registre de circuits pour nos segments (R3-A2) ;
quel coût par étape et quelle taille de preuve avec le monorepo courant (R3-A3) ; comment
recalculer le `output_hash` racine depuis les préimages des feuilles (R3-A4) ; quel plan B (R3-A8).

## Verdict : **GO** (avec deux points d'attention chiffrés)

- La chaîne complète fonctionne sur nos propres feuilles pour N = 1, 2, 3, 4 (repli impair et
  auto-repli inclus) : racine acceptée par le vérifieur Cairo, `packed_output` recomposé octet à
  octet en Cairo, `VerificationOutput.output_hash` reproduit exactement pour chaque N.
- Coût on-chain **constant** : 5,26–5,37 M steps + ~510 k range_check quelle que soit N.
- Registre `doom` généré en 6,9 s / 8,0 GB, **byte-identique à la régénération** ; multiverifier =
  celui de la production (les constantes du vérifieur on-chain restent valables).
- Recomposition on-chain : **5 645 steps pour N = 4, 68 315 steps pour N = 50** (mesuré, pas extrapolé).
- Points d'attention : (1) le vérifieur du monorepo coûte **5,3 M steps** (pas 3,8 M) et la preuve
  racine fait **~94 k felts** (pas 36 k) — S5 doit refaire le découpage en phases et le staging ;
  (2) chaque preuve de circuit (feuille comme repli) monte à **32,5 GB de RSS** : un serveur 32 GB
  ne suffit pas, il faut 48–64 GB (ou une réduction mémoire côté prouveur).

## Flux de données (lu dans le code, cd7bc5f)

### 1. Exécutable Scarb + args → feuille (`leaf-prover`)

```
segment.executable.json + args.json            (scarb build ; args = tableau JSON de felts hex)
   │  bl_input.json : PrivacySimpleBootloaderInput
   ▼
leaf-prover --program leaf_simple_bootloader_compiled.json --program_input bl_input.json
            --circuit_registry_json registry.json --output_path leaf.raw.json
```

- **Programme bootloader** : `crates/stwo_run_and_prove_recursive_tree/test_data/leaf_simple_bootloader_compiled.json`
  (Cairo 0, 1,5 MB, construit dans le dépôt interne StarkWare `c9180c2c…` cible
  `//src/starkware/cairo/bootloaders/simple_bootloader:leaf_simple_bootloader_program`, hash de programme
  Blake `1295276242458012971975387023502514236353931151874237036512262876792126013758`, épinglé par
  `tests.rs::test_leaf_simple_bootloader_program_hash_snapshot`). Le source Cairo 0 n'est **pas** dans le
  monorepo ; ses hints sont dans `crates/cairo-program-runner-lib/src/hints/privacy_simple_bootloader_hints.rs`.
  Il exécute la tâche, calcule son hash de programme (`compute_program_hash_chain` :
  Blake2s sur `[0, main, n_builtins, builtins…, bytecode…]` de l'entrypoint `Bootloader` de
  l'exécutable), forme la **préimage** `[program_hash, task_output…]`, la hache en Blake2s après
  encodage Cairo 0 des felts, et écrit le digest 256 bits dans **2 cellules de sortie de 128 bits**
  (`N_OUTPUTS = 2`, `N_WORDS_PER_OUTPUT_CELL = 4`).
- **`program_input`** (`PrivacySimpleBootloaderInput`, `hints/types.rs`) :

  ```json
  {"tasks": [{"type": "Cairo1Executable", "path": "<...>.executable.json",
              "user_args_file": "args.json",          // ou "user_args_list": [nombres JSON]
              "program_hash_function": "blake"}],
   "fact_topologies_path": null, "single_page": true,
   "output_preimage_dump_path": "preimage.json"}
  ```

  Le hint `dump_privacy_simple_bootloader_output_preimage` écrit `preimage.json` = liste de felts hex
  `[program_hash, out_0, …]`. (L'ancien « privacy simple bootloader » de modeofO dumpait
  `[n_tasks, task_size, program_hash, out…]` ; le *leaf* bootloader ne garde que `[program_hash, out…]`,
  confirmé par le golden `leaf_preimage.json`.) Types de tâche acceptés : `Cairo1Executable`,
  `RunProgramTask` (Cairo 0), `CairoPiePath` ; un PIE Cairo 1 reste rejeté (cf. modeofO).
- **`leaf-prover`** (`crates/leaf_prover/src/prove_leaf.rs`) : exécute (layout `all_cairo_stwo`, proof
  mode), adapte, **exige exactement 2 cellules de sortie**, forme `output_hash` (8 mots u32 : les 4 mots
  bas de chaque cellule), prouve avec `prove_cairo::<Blake2sM31MerkleChannel>` et les
  `cairo_prover_params` du registre (`canonical_small`, `include_all_preprocessed_columns`,
  `lifting_size_policy = at_least_preprocessed` → **toute exécution ≤ 2^20 steps est liftée à 2^21 et
  a `trace_log_size = 20`** ; c'est ce qui rend le registre à taille unique suffisant). Il choisit
  `registry.leaf_verifiers[trace_log_size]`, construit le circuit vérifieur Cairo
  (`leaf_verifier_config` : programme bootloader en constantes, racine pré-traitée, composants = tous
  sauf les 4 Pedersen-18 pour `canonical_small`), le remplit avec la preuve, le **padde**
  (`pad_to_targets`) aux `component_log_sizes` du registre, le prouve (canal Blake2sM31, FRI du
  registre : pow 26, blowup 1, 70 requêtes, fold 4) et **vérifie que `circuit_hash` == entrée du registre**.
- **Sortie** `SerializedLeafProof` (`crates/leaf_proof_format`) : `{circuit_preprocessed_root: 8 mots hex,
  circuit_hash: 8 mots hex, proof: base64(Proof<QM31> sérialisé)}` — 546 KB pour nos feuilles.
- **`LeafInput`** (`leaf_io.rs`) = `SerializedLeafProof` aplati + `output_preimage: [felts décimaux]`,
  injecté par le backend (ici `scripts/inject_preimage.py`). Le tree **recalcule** la sortie de la
  feuille : `H1 = blake2s(encode_felts_to_u32s(preimage))` (encodage `starknet_types_core::Blake2Felt252`).

### 2. Repli (`stwo_run_and_prove_recursive_tree`)

```
leaves.json = {"leaves": ["leaf_0.json", …]}   (ordre = ordre de repli)
stwo_run_and_prove_recursive_tree --program_input leaves.json --circuit_registry_json registry.json
    --proof_path root.proof --program_output program_output.json --packed_output_path packed_output.json
```

- `CanonicalCircuit::build` : construit **le** multiverifier (2 entrées) paddé aux cibles du registre,
  vérifie la parité de layout (feuille et multiverifier ont la même trace pré-traitée,
  `trace_log_size = 23`) et que son hash == `registry.multiverifiers[0]`.
- Nœud = `(proof, preprocessed_root, output_values[8])`. `reduce_pair` construit
  `build_multiverifier_circuit([gauche, droite])` : pour chaque enfant, `CircuitStatement` =
  config partagée + racine pré-traitée de l'enfant + ses 8 mots de sortie, vérification STARK
  en-circuit, puis **sortie du nœud = blake2s(circuit_hash_g ‖ out_g ‖ circuit_hash_d ‖ out_d)**
  (32 mots u32 = 128 octets, mots hachés en little-endian). `circuit_hash =
  blake2s(log_blowup(1 octet) ‖ component_log_sizes(11 octets) ‖ preprocessed_root(32 octets))`.
- Plis internes : canal **Blake2sM31**, preuve resérialisée `Proof<QM31>` ; **pli racine** (dernière
  réduction, `is_root`) : canal **Blake2s** standard (celui que le vérifieur Cairo implémente),
  sérialisé par `prepare_circuit_proof_for_cairo_verifier` en **flux felt252 hex JSON** =
  `--arguments-file` du vérifieur.
- Topologie : couches successives, paires adjacentes gauche→droite ; **entrée impaire reportée telle
  quelle** à la couche suivante (possible car tous les nœuds ont la même forme) ; **N = 1 : la feuille
  est repliée avec elle-même** (même preuve dans les deux fentes). Profondeur ⌈log₂ N⌉, N − 1
  réductions (1 pour N = 1).
- Sorties : `root.proof` (felts), `program_output.json` (8 u32 = sortie brute de la racine),
  `packed_output.json` : `Composite{circuit_hash, subtasks}` par nœud vérifieur, jusqu'à
  `Composite{leaf_hash, [Plain{output_preimage}]}` par feuille — tout digest est recomputable.

### 3. Vérifieur on-chain (`stwo_cairo_verifier/crates/circuit_verifier`)

`main(proof: CircuitProof) -> VerificationOutput` : lit `preprocessed_commitment` et
`output_values` ; `circuit_hash = compute_circuit_hash(log_blowup, preprocessed_commitment)` avec
`COMPONENT_LOG_SIZES` **codés en dur** (`circuit_air/src/multiverifier_consts.cairo`, générés depuis
`circuit_registry_definitions/production` par `circuit_params/tests/cairo_consts_test.rs`) ;
`verify_circuit` avec `PREPROCESSED_COLUMN_LOG_SIZES` et `circuit_pcs_config()` (pow 26, blowup 1,
70 requêtes, fold 4) codés en dur ; puis
**`output_hash = blake2s(circuit_hash ‖ mots de sortie)`** (`get_verification_output`, chaque sortie
vérifiée comme u32 packé `(lo16, hi16, 0, 0)`). Conséquence : **le contrat consommateur doit épingler
le hash du multiverifier** (celui de `packed_output` racine) et le hash du circuit feuille, et
recomposer la sortie racine depuis les préimages.

### 4. Recomposition (`spikes/s4/recursion_outputs`)

`root_output_hash(preimages, leaf_hash, mv_hash)` : `leaf_node` → `H1` ; `fold_tree` (paires, report
impair, auto-repli) ; `verification_output_hash = blake2s(mv_hash ‖ root.output)`. Le consommateur
compare ce hash au `output_hash` enregistré par le fact registry, vérifie `preimage[0] ==
program_hash(segment)`, la chaîne `h_out[i] == h_in[i+1]` et `status`.

| Registre | Cibles (log) eq / qm31_ops / m31_to_u32 / triple_xor / blake_g_gate | Hash feuille (log 20) | Hash multiverifier | Génération |

| `doom_min` : idem sans `pad_to` (padding minimal) | 20 / 23 / **20** / **19** / 23 | `700e2f2b…585ef31f` | `976fb1bb…a791ee7c` (différent) | 10,3 s / 7,9 GB |
| `doom_19_20` : plage 19–20 | — | **panique** `constraint_eval.rs:72 index out of bounds (len 20, index 20)` | — | — |
| `canonical_small` (monorepo, pow 16) | 20 / 23 / 21 / 20 / 23 | `d2d85a42…60f3baea` | `a5989715…973f680f` | — |

Lecture :

- Le rapport de tailles (`report.txt`) pour une feuille log 20 : eq 2^20 (61 %), qm31_ops 2^23 (77 %),
  m31_to_u32 2^20 (93 %), triple_xor 2^19 (99 %), blake_g_gate 2^23 (62 %) ; multiverifier seul :
  16 / 21 / 19 / 18 / 22. **Le padding minimal ne gagne qu'un bit sur deux petits composants** : on
  garde la forme production (`pad_to`), ce qui rend le multiverifier — et donc les constantes codées en
  dur du vérifieur on-chain et les classes de modeofO — **identiques à la production**. Seul le hash du
  circuit **feuille** est propre à `doom` (il épingle le bootloader, la trace pré-traitée `canonical_small`
  et pow 26 pour la preuve Cairo, contre pow 16 dans `canonical_small`).
- **La plage 19–20 est impossible** : les colonnes de séquence de `canonical_small` sont à log 20, la
  feuille log 19 n'existe pas (`min_trace_log_size` borné à 20, cf. commentaire de
  `generate_circuit_registries.py`). Avec `at_least_preprocessed`, toute exécution ≤ 2^20 steps est de
  toute façon liftée à log 20 : **un seul circuit feuille, aucune conséquence de padding entre segments**
  courts et longs (la preuve Cairo d'un stub de 145 k steps coûte 2,0 s ; celle d'un segment de 2^20
  coûtera quelques secondes de plus, le circuit feuille est identique).
- Déterminisme : `run_all.sh` régénère `doom/registry.json` en fin de campagne (14,3 s sous
  contention) et le compare au premier : **byte-identique** (même machine ; le critère « 2 machines »
  de R3-A2 reste à faire en CI, R3-A5).

Détail d'une feuille (N = 1, sans contention) : exécution + adaptation < 0,1 s ; **preuve Cairo du
bootloader 2,04 s** ; construction/remplissage du circuit vérifieur ~0,4 s ; **preuve du circuit
~18 s** ; RSS 32,5 GB (trace de circuit 2^23 lignes). Preuve de feuille : **545 896 octets**.
`CanonicalCircuit::build` : 4–11 s (une fois par repli).

Constats :

- **Coût on-chain constant** : 5,26–5,37 M steps (±1 %) pour N = 1…4, range_check 506–519 k ; il ne
  dépend ni de N ni du programme (topologie fixe). C'est **+40 % par rapport aux 3,8 M steps** de
  CONTEXT §6.2 : avec le ratio gas/step observé par modeofO en production (1,69e9 gas pour 3,8 M
  steps ≈ 445 gas/step, builtins compris), on attend **≈ 2,3e9 L2 gas** → **3 tx de vérification**
  (plafond 1,21e9/invoke) au lieu de 2, à valider sur devnet en S5.
- **Preuve racine 93–95 k felts** (×2,6 modeofO) : le staging calldata passe de ~8 à **~19 tx de
  5 000 felts** (ou moins avec un packing 7 u32/felt : les felts sont des mots ≤ 32 bits, cf. `0x1799`),
  et le nombre de slots de stockage suit — c'est le poste de coût qui a le plus bougé.
- **Mémoire** : 32,5 GB pour chaque preuve de circuit ; deux preuves simultanées ne tiennent pas sur
  64 GB (d'où le verrou) ; un serveur **32 GB est exclu** sans travail côté prouveur.
- **Temps wrap** (machine dédiée, sans contention) : feuille ≈ 22 s, réduction ≈ 30 s →
  N = 8 : 8 × 22 + 7 × 30 ≈ **6,5 min** (objectif PLAN « < 5 min sur 32 GB » manqué sur les deux
  axes) ; N = 25 : ≈ 21 min ; **N = 50 : ≈ 43 min** séquentiel. Parallélisme possible seulement avec
  ≥ 40 GB par preuve concurrente (les feuilles sont indépendantes ; les couches de l'arbre aussi).
- La variance N = 3 (26 → 68 s par feuille, repli 103 s) vient de builds Rust concurrents d'autres
  agents (2 `rustc` à 80 % CPU au moment de la mesure), pas du pipeline.

## Plan B (R3-A8) : ⌈N/2⌉ faits avec le multiverifier 2 entrées

Si `stwo_run_and_prove_recursive_tree` régresse (topologie, format felts, hash) mais que `leaf-prover` et
le vérifieur Cairo restent alignés, on soumet **un fait par paire de feuilles** : pour chaque paire
(2i, 2i+1) on lance le tree sur **2 feuilles seulement** — `printf '{"leaves":["leaf_2i.json","leaf_2i+1.json"]}' > pair_i.json ;
stwo_run_and_prove_recursive_tree --program_input pair_i.json --circuit_registry_json doom/registry.json --proof_path root_i.proof --program_output out_i.json --packed_output_path packed_i.json`
(pour une feuille orpheline : `{"leaves":["leaf_N-1.json"]}`, auto-repli) — c'est exactement le wrap
« 2 entrées » de modeofO, produit sans bootloader ni bridge, puis `scarb --profile proving execute -p stwo_circuit_verifier --features qm31_opcode --arguments-file root_i.proof`
et **⌈N/2⌉ soumissions** au registry (`stage_proof`/`verify_phase*`) ; `DoomRuns` accepte alors une
liste de ⌈N/2⌉ faits et recompose chacun avec `recursion_outputs::fold_tree` sur 1 ou 2 feuilles
(la même bibliothèque, N ≤ 2) en vérifiant la chaîne `h_in/h_out` **entre** les faits. Coût on-chain
× N/2 (≈ 25 × 2,3e9 gas pour 50 segments) : praticable seulement pour des parties courtes ou en
mode dégradé. Variante intermédiaire : arbre côté serveur en passes successives (`tree` sur des
sous-groupes de 2^k feuilles, puis les racines ne sont **pas** re-repliables car sérialisées pour
Cairo — il faudrait garder la sortie `Proof<QM31>` interne, ce que le binaire ne fait pas aujourd'hui :
patch d'une dizaine de lignes dans `fold.rs` si nécessaire). Démonstration archivée : les runs
N = 1 (auto-repli) et N = 2 de `results/` sont précisément ces deux formes de fait.

## Blocages et écarts

1. **Aucun blocage fonctionnel.** Le registre `production` est inutile pour nous (log 25–29) ; `doom`
   (log 20, forme production) est généré, reproductible et accepté par `leaf-prover` sans modification
   du monorepo (les binaires n'ont besoin que de `registry.json`).
2. **Coûts on-chain revus à la hausse** (5,3 M steps, 94 k felts) : à intégrer dans CONTEXT §6.2 et
   S5 (probablement 3 tx de vérification + ~19 tx de staging par fait).
3. **Mémoire prouveur 32,5 GB/preuve de circuit** : dimensionnement du wrapper (U8) à revoir (64 GB) ;
   piste : profiler `prove_circuit_assignment` (colonnes de base 2^23 × ~150 colonnes + blow-up).
4. **Prouveur Scarb 2.16 ≠ monorepo** : le stub écrit des felts ≥ 2^128 (poseidon) en mémoire et
   utilise range_check ; le prouveur du monorepo (Blake2sM31, canonical_small) l'a accepté — indice
   favorable pour U6/S0, à confirmer avec le bitwise.
5. Le bootloader feuille n'a pas de source public : on dépend du JSON compilé et de son hash épinglé
   dans les tests upstream ; le hash du circuit feuille `doom` l'épingle transitivement.
